# Подключение источников рекламы — инструкция оператора

Состояние на 18.10.2026. Как включить каждый источник публикаций, проверить его и что делать при ошибке. Требования — план подключения от 16.10.2026, краткий обзор и таблица статусов — раздел «Подключение источников рекламы» в [README](../README.md). Реальных ключей, паролей, сессий и телефонов в этом документе нет: только имена переменных.

## 1. Как устроено

```text
Instagram — Meta Graph API ───────┐
Telegram-каналы — MTProto ────────┤  воркер: задания «проверка» и «сбор»
TikTok — Apify (платно) ──────────┤  (по кнопке администратора или по расписанию)
Krisha.kz — HTML выдачи ──────────┘
Telegram-бот заявок ── POST /api/intake/telegram ─────┐
Внешний сборщик ────── POST /api/intake/publications ─┤
                                                       ▼
        единый приём: дедупликация по внешнему ID, версии, файлы → БД + хранилище MEDIA_ROOT
                                                       ▼
        задание анализа: файлы → кадры видео (ffmpeg) → OCR (Tesseract) → правила saq-ai-1
                         → Claude (Anthropic), если задан ANTHROPIC_API_KEY: гипотезы с цитатами
                                                       ▼
        публикация «Новая» в ленте, гипотезы ИИ и журнал от «Системы» → решение аналитика → балл → сигнал → PDF

2ГИС → кандидаты адреса в карточке ЖК → выбор аналитика (координаты меняются только явным решением)
OLX → OAuth собственного аккаунта, без чтения чужих объявлений
Claude (Anthropic) → этап «llm» задания анализа: гипотезы для аналитика, не решения
```

- **Два процесса.** API (`uvicorn app.main:app`) отдаёт состояние, принимает публикации и заявки и ставит задания в таблицу `jobs`. Воркер (`python -m app.worker`) — единственный, кто выполняет проверки, сбор и анализ, и единственный планировщик. В HTTP-запросе пользователя сбор не выполняется: «Проверить подключение» и «Собрать сейчас» отвечают 202 и номером запуска.
- **Таблицы.** `collectors` (подключение: настройки, состояние, отметка «остановлен»), `collection_runs` (запуски: время, статус, счётчики, ID запуска Apify, стоимость), `ingest_items` и `ingest_versions` (исходная запись и история изменений), `media_assets` (файлы), `jobs`, `worker_leases`, `oauth_states`, `integration_tokens`, `geo_checks`, `bot_submissions`, `quota_counters`. С таблицами демо-набора они связаны только по `ads.id` (без внешних ключей).
- **Собранная публикация.** `origin = collected`, `source = parser` (сборщики и приём через API) или `bot` (заявка жителя), статус `new`. Привязку к ЖК анализ не назначает: гипотезы ИИ видны аналитику, решение — за ним (`SAQ_COLLECTED_AUTOLINK=1` включает правило ручного ввода только для демонстрации). Автор автоматических событий журнала — «Система»; имя «Система» людям на новых маршрутах использовать нельзя.
- **Сбой ≠ «нет новых».** Ошибка ключа, закрытый канал, изменившаяся разметка, запрет robots.txt, проверка доступа на сайте — это статус ошибки источника, а не пустая выдача. «Нет новых» — только запуск без ошибок и без записей.

## 2. Статусы подключения

| Статус | Что значит | Что делать |
|---|---|---|
| не настроен | На сервере нет переменных (их имена показаны в карточке) или условия (сессии Telegram) | Заполнить `.env`, перезапустить API и воркер |
| не проверен | Ключи есть, проверки ещё не было или ключи изменились после неё | «Проверить подключение» |
| в очереди / проверяется / идёт сбор | Задание ждёт воркер или выполняется | Ждать; если долго «в очереди» — проверить, запущен ли воркер (раздел 5) |
| готов к сбору (у 2ГИС и Claude — «готов») | Проверка прошла | Настроить списки, «Собрать сейчас» или включить «Сбор по расписанию» |
| работает | Последний сбор успешен; у бота — «принимает заявки», у приёма API — «принимает публикации», у Claude — «анализирует публикации» (последний запрос успешен) | — |
| работает частично | Часть данных недоступна: закрытый канал, карточки Krisha за проверкой доступа, окно выдачи TikTok | Прочитать заметки запуска |
| ожидает заявок / ожидает публикаций | Приёмник настроен, данных ещё не было | — |
| ошибка | Сбой источника или ошибка настроек | Текст ошибки в карточке и в журнале; исправить, «Проверить подключение» |
| истёк доступ | Токен истёк (Meta, OLX) или Anthropic отклонил ключ (HTTP 401) | Обновить токен или ключ (разделы 4.1, 4.7, 4.9) |
| нет доступа | У токена нет разрешений или клиент приёма/бот присылает неверный токен | Проверить разрешения и токены |
| нужно ручное действие | Сайт закрыл страницы проверкой доступа (Krisha) | Раздел 4.5; обход не выполняется |
| пауза: лимит запросов | Источник ограничил частоту (Graph API, FloodWait Telegram, 2ГИС); у Claude — «пауза: лимит»: исчерпан дневной бюджет `ANTHROPIC_DAILY_BUDGET_USD` | Сбор продолжится после указанного времени; анализ ИИ — после полуночи по Усть-Каменогорску |
| не используется | Claude: `ANTHROPIC_DAILY_BUDGET_USD = 0` — анализ ИИ выключен | Задать бюджет больше нуля |
| остановлен (метка) | Платный сбор после ошибки или ошибка настроек: расписание не запускает сбор | Исправить причину, «Проверить подключение» (снимает остановку при успехе) |

У OLX свои подписи: «заявка отправлена» (ключей нет), «не подключён» (ключи есть, OAuth не пройден), «подключено · ограничено» (аккаунт подключён; это не сбор чужих объявлений). Статусы запуска: в очереди, выполняется, успешно, частично, ошибка, проверка доступа на сайте, пауза: лимит запросов, не настроен, отменён.

Если ключ на сервере сменился после последней успешной проверки, карточка пишет «Ключи на сервере изменились после последней проверки — перезапустите воркер и нажмите «Проверить подключение»», и сбор по расписанию не запускается до новой проверки.

## 3. Общая подготовка

### 3.1. Файл `.env`

```bash
cp .env.example .env            # в корне репозитория; .env — вне Git и вне Docker-образа
python3 -c "import secrets; print(secrets.token_urlsafe(32))"   # по отдельному значению на каждый токен
```

- Значения пишутся без кавычек и читаются буквально. Пустое значение — то же, что не задано: подключение «не настроено» и ничего не запрашивает.
- Три токена доступа: `SAQ_ADMIN_TOKEN` (администратор подключений), `INTEGRATION_INGEST_TOKEN` (внешние сборщики), `SERVICE_API_TOKEN` (бот заявок). Каждый — не короче 24 символов и не меньше 12 разных; токен администратора не может совпадать с двумя другими. Слабый или совпадающий токен считается не заданным (предупреждение в журнале API называет переменную, но не значение).
- Настройки читаются один раз при старте процесса. После правки `.env`: в Docker — `docker compose up -d api worker`, локально — перезапуск `./dev.sh`.
- Docker передаёт `.env` в `api` и `worker` через `env_file` (формат `raw`, без подстановок). `MEDIA_ROOT` и `TG_SESSION_PATH` в Docker задаёт `docker-compose.yml` (`/data/media`, `/data/private/telegram.session`) — значения из `.env` для них не действуют. Локально приложение само читает `.env` из корня репозитория (в окружение оболочки он не загружается); другой файл — `SAQ_ENV_FILE`.

### 3.2. Режим администратора в интерфейсе

Настройка подключений и ручной запуск — только администратору; вход аналитика этого права не даёт.

1. `/sources` → раздел «Подключения» → «Режим администратора» → ввести значение `SAQ_ADMIN_TOKEN`. Сервер проверяет его (`GET /api/admin/check`); токен хранится только в `sessionStorage` этой вкладки до её закрытия и уходит заголовком `X-Admin-Token` лишь в маршруты администратора.
2. Действия в карточке подключения: «Проверить подключение», «Настроить» (аккаунты, каналы, профили, URL поиска; «Период сбора, минут»), «Сбор по расписанию», «Собрать сейчас»; в шапке раздела — «Обновить всё» (сбор для включённых, настроенных и проверенных сборщиков, остальные — с причиной пропуска). У OLX — «Подключить аккаунт OLX». Автор действий — вошедший аналитик.
3. Без `SAQ_ADMIN_TOKEN` на сервере маршруты администратора отвечают 503 «Администрирование подключений не настроено: задайте SAQ_ADMIN_TOKEN на сервере».

Из консоли — тот же заголовок (или `Authorization: Bearer`):

```bash
curl -s -X POST http://127.0.0.1:8000/api/sources/krisha/test \
  -H "X-Admin-Token: <SAQ_ADMIN_TOKEN>" -H "Content-Type: application/json" -d '{"author": "Имя аналитика"}'
```

Порядок для любого сборщика: ключи в `.env` → перезапуск → «Проверить подключение» → «готов к сбору» → «Настроить» → «Собрать сейчас» или «Сбор по расписанию».

### 3.3. Проверка из консоли

```bash
cd backend && .venv/bin/python -m app.integrations.smoke              # все подключения
cd backend && .venv/bin/python -m app.integrations.smoke dgis krisha  # выбранные
docker compose exec worker python -m app.integrations.smoke           # в Docker: у воркера есть том сессии Telegram
```

Коды: `instagram`, `telegram`, `tiktok`, `krisha`, `telegram_bot`, `intake`, `dgis`, `anthropic`, `olx`. Для каждого — «код: статус — пояснение» и несекретные сведения. Без ключей сеть не используется. Публикации не сохраняются, но запросы к источникам настоящие: 2ГИС расходует квоту в кабинете (локальный счётчик не учитывает), Krisha получает обычные запросы, Apify — только чтение аккаунта и цен Actor, без платного запуска; Anthropic — только сведения о модели (`models.retrieve`), без генерации и без оплаты. Код выхода 0 (это отчёт), 2 — неизвестный код. Значения ключей не печатаются.

## 4. Подключения

### 4.1. Instagram — Meta Graph API · Business Discovery

**Переменные.** `META_USER_ACCESS_TOKEN` (обязательно). `META_APP_ID` и `META_APP_SECRET` — по желанию: с ними срок токена проверяется токеном приложения, а к каждому запросу добавляется `appsecret_proof`. `META_GRAPH_VERSION` (по умолчанию `v26.0`). Где искать наш Instagram: `META_IG_USER_ID` (17840000000000001), иначе Страницы токена с учётом `META_PAGE_ID` (1000000000000002), иначе Страницы бизнес-портфолио `META_BUSINESS_ID` (1000000000000001). Лимиты: `IG_PAGE_SIZE` (25 публикаций на запрос), `IG_FIRST_LOAD_MAX` (50 при первой загрузке аккаунта).

**Получить токен.**

1. [Graph API Explorer](https://developers.facebook.com/tools/explorer/) под аккаунтом Facebook с ролью в приложении и на Странице. «Meta App» — приложение проекта (его App ID — `META_APP_ID`), «User or Page» — «User Token».
2. Разрешения: обязательные `instagram_basic`, `instagram_manage_insights`, `pages_read_engagement`; рекомендуемые `pages_show_list`, `business_management` (без них Страница находится только по `META_IG_USER_ID` или `META_BUSINESS_ID`). Если роль на Странице выдана через Business Manager, Meta требует ещё `ads_read` или `ads_management`. «Generate Access Token» и подтвердить доступ к Странице и Instagram.
3. Полученный токен краткосрочный (около часа). В [Access Token Debugger](https://developers.facebook.com/tools/debug/accesstoken/) вставить его, «Debug» — проверить App ID, Scopes и Expires, затем «Extend Access Token»: получится долгосрочный токен (около 60 дней). То же сервером: `GET https://graph.facebook.com/v26.0/oauth/access_token?grant_type=fb_exchange_token&client_id=<META_APP_ID>&client_secret=<META_APP_SECRET>&fb_exchange_token=<краткосрочный токен>` — выполнять только на сервере, App Secret не вводить в браузере. Вместо пользовательского токена можно выпустить токен системного пользователя в Business Manager с теми же разрешениями.
4. Записать токен в `META_USER_ACCESS_TOKEN`, перезапустить API и воркер, «Проверить подключение». Успех: «Подключено: @… Токен действует до ДД.ММ.ГГГГ».
5. «Настроить» → аккаунты наблюдения (`@имя` или ссылка `instagram.com/имя`, только профессиональные аккаунты) → «Собрать сейчас» или «Сбор по расписанию» (по умолчанию раз в час, от 30 минут до суток).

**Продление.** Пока сбор включён, воркер раз в сутки проверяет токен (`debug_token`). За 7 дней до истечения в карточке появляется «Токен истекает ДД.ММ.ГГГГ — продлите его», при скором окончании доступа к данным — «Доступ к данным истекает … — пройдите вход Meta заново». Продление — те же шаги 1–4: новый токен в Explorer, «Extend Access Token», замена в `.env`, перезапуск, «Проверить подключение». Токен, истекающий в ближайшие сутки, включить не даст: «Токен Meta краткосрочный — получите долгосрочный (60 дней) или токен системного пользователя». Истёкший или отозванный токен — статус «истёк доступ».

**Поведение.** Запросы — на `graph.facebook.com/{META_GRAPH_VERSION}/`, токен только в заголовке `Authorization: Bearer`. Ссылки на файлы временные, поэтому файлы скачиваются при сборе (только с CDN Instagram/Facebook). Карусели — со слайдами; если Business Discovery слайдов не отдаёт, сохраняется первое изображение с заметкой (вживую это не проверялось — токена ещё нет). При использовании лимита Graph API от 80 % запуск прекращает запросы, следующий откладывается на час. Таргетированные показы конкретным людям так не видны — только публикации аккаунтов из списка.

### 4.2. Telegram-каналы — MTProto (Telethon)

**Переменные.** `TG_API_ID`, `TG_API_HASH` — с [my.telegram.org](https://my.telegram.org) («API development tools») выделенного аккаунта для чтения каналов. `TG_PHONE` — номер этого аккаунта, нужен только для входа. `TG_SESSION_PATH` — файл сессии (локально по умолчанию `backend/data/private/telegram.session`, в Docker — `/data/private/telegram.session` на томе `tgsession`, смонтированном только в воркер). Лимиты: `TG_HISTORY_LIMIT` (50 сообщений канала в первый запуск), `TG_EDIT_WINDOW` (правки среди последних 30 сообщений), `TG_MAX_VIDEO_MB` (50), `TG_DOWNLOAD_TIMEOUT_S` (300). `BOT_TOKEN` для сбора каналов не подходит.

**Вход — один раз, по коду.** Сессией одновременно пользуется только один процесс (блокировка `<путь>.lock`), поэтому воркер на время входа останавливают. Код приходит в приложение Telegram или SMS на телефон аккаунта; владелец сообщает его в течение 15 минут (дальше ожидание кода устаревает). Не пересылайте код сообщением в самом Telegram — Telegram может отклонить такой вход.

Локально (воркер остановлен: `./dev.sh` выключен или запущен с `SAQ_WORKER=0`):

```bash
cd backend
.venv/bin/python -m app.integrations.telegram_login --send-code    # «Код отправлен (…). Введите: … --code <код>»
.venv/bin/python -m app.integrations.telegram_login --code 12345   # код из Telegram или SMS
.venv/bin/python -m app.integrations.telegram_login --password     # только если ответ «Нужен пароль двухфакторной защиты»
.venv/bin/python -m app.integrations.telegram_login --status       # «Сессия есть: @имя»
```

В Docker:

```bash
docker compose stop worker
docker compose run --rm worker python -m app.integrations.telegram_login --send-code
docker compose run --rm worker python -m app.integrations.telegram_login --code 12345
docker compose run --rm worker python -m app.integrations.telegram_login --password   # пароль вводится скрыто
docker compose run --rm worker python -m app.integrations.telegram_login --status
docker compose up -d worker
```

Без аргументов команда проходит вход за один запуск: запрашивает код и пароль в терминале. `--force` — войти заново при существующей сессии, `--logout` — выйти и удалить файл сессии. Коды выхода: 0 — готово, 1 — ошибка, 2 — не заданы `TG_API_ID` / `TG_API_HASH` / `TG_PHONE`, 3 — нужен пароль 2FA, 4 — неверный код или пароль, 5 — код устарел (снова `--send-code`), 6 — Telegram просит подождать, 7 — сессия занята воркером. Номер, код и сессия не печатаются.

**После входа.** Запустить воркер → «Настроить» → каналы (`t.me/имя`, `@имя` или ссылка; только публичные, ссылки-приглашения отклоняются) → «Проверить подключение» → «Собрать сейчас» или расписание (по умолчанию раз в 30 минут, от 15 минут до суток). Файл сессии создаётся с правами 0600 в каталоге 0700; это секрет — в Git и в резервные копии его не кладут, при потере проще войти заново.

**Поведение.** Первый запуск — последние `TG_HISTORY_LIMIT` сообщений, дальше — только новые после сохранённой позиции и правки в окне `TG_EDIT_WINDOW`. Альбом — одна публикация (ID «канал:первое сообщение») со всеми файлами. FloodWait — «пауза: лимит запросов» без повторов внутри запуска. Закрытый или несуществующий канал — «работает частично» с причиной; если недоступны все — ошибка настроек.

### 4.3. Telegram-бот заявок — приёмник `POST /api/intake/telegram`

> **Контракт не сверен с адаптером `saq-telegram-bot`** (`integration/telegram_intake.py`): проекта бота на этой машине нет. Ниже — то, что реализует приёмник этой версии API. Перед подключением бота сверить маршруты, заголовок и формат тела с кодом адаптера.

- **Переменная.** `SERVICE_API_TOKEN` — тот же секрет, что `SERVICE_API_TOKEN` в настройках бота. Свои переменные бот читает сам (`BOT_TOKEN`, `ADMIN_USER_IDS`, `ADMIN_CHAT_ID`, `SERVICE_URL`, `SERVICE_API_TOKEN`); `INTEGRATION_INGEST_TOKEN` с ним не совместим.
- **Доступ.** `Authorization: Bearer <SERVICE_API_TOKEN>` или `X-API-Key: <SERVICE_API_TOKEN>`. Нет секрета на сервере — 503, нет заголовка — 401, неверный — 403. Отказы видны в карточке: бот с неверным токеном — «нет доступа», отклонённая заявка — «ошибка», а не «ожидает заявок».
- **Маршруты.** `POST /api/intake/telegram` — заявка: `application/json` (до 1 МБ, без файлов) или `multipart/form-data` с полем `payload` (JSON заявки) и повторяющимся полем `files` (до 10 файлов по 20 МБ; JPEG, PNG, WEBP, GIF, MP4, MOV; тип — по содержимому). `GET /api/intake/telegram/submissions/{externalId}` — статус заявки. `GET /api/intake/telegram/updates?since=<ISO с поясом>&limit=1..500` — заявки, статус которых изменился позже `since`.
- **Тело заявки.** `externalId` (повторяемый ID от бота, например «chat_id:message_id»), `submittedAt`, `platform` (`instagram`, `telegram`, `tiktok`, `krisha`, `olx`, `facebook`, `other`), `account`, `url`, `text`, `comment`, `applicant` (`telegramUserId`, `chatId`, `username`, `name`, `phone`), `media` (описание файлов по порядку: `key`, `fileName`, `mime`). Поля решений аналитика и неизвестные поля — 422.
- **Ответы.** Новая заявка — 201 `created`, повторная доставка — 200 `unchanged` (копия не создаётся), изменённая — 200 `updated` (новая версия). Статусы для жителя: `received`, `in_review`, `confirmed`, `dismissed` с русскими подписями.
- **Хранение.** Публикация попадает в общую ленту (`source = bot`, статус «Новая», без привязки к ЖК) и в очередь анализа. Данные заявителя и его комментарий — только в `bot_submissions`: в публикации, журнале и ответах API их нет. Аккаунт и ссылка со слов жителя в гипотезе ЖК не учитываются.
- **`SERVICE_URL` бота.** Не `localhost` внутри контейнера бота. Если бот в Docker и подключён к сети этого compose-проекта (внешняя сеть `codemasters8_default`), адрес API — `http://api:8000`; если бот запущен на этой же машине без Docker — `http://127.0.0.1:8000` (API опубликован только на 127.0.0.1). Нужен ли в `SERVICE_URL` префикс `/api`, решает адаптер — сверить.
- **Один экземпляр.** На один токен бота — один процесс long polling; webhook и polling одновременно не использовать.

### 4.4. TikTok — Apify, Actor `clockworks/tiktok-scraper` (платно)

**Переменные.** `APIFY_TOKEN` — личный API-токен из Apify Console (Settings → API & Integrations). `APIFY_ACTOR_ID` (по умолчанию `clockworks~tiktok-scraper`). Ключи TikTok Developer не нужны. Input без секретов — `backend/app/integrations/tiktok_input.json` (новые публикации профиля, видео, обложки и изображения слайд-шоу).

**Защита от расходов.**

- `APIFY_MAX_TOTAL_CHARGE_USD` (0,5) — лимит на один запуск; передаётся Apify как есть и никогда не повышается. Меньше минимума Actor или больше дневного лимита — ошибка настроек с пояснением.
- `APIFY_DAILY_BUDGET_USD` (1,0) — лимит на сутки по времени Усть-Каменогорска. Учитываются и неудачные оплаченные запуски, и запуски с неизвестной стоимостью (по лимиту на запуск). Исчерпан — «Дневной лимит расходов Apify (…) исчерпан».
- `APIFY_MAX_ITEMS_PER_PROFILE` (5) — публикаций с профиля за запуск; если все они новые, более ранние могли выпасть — запуск «частично». `APIFY_RUN_TIMEOUT_S` (300) — после срока запуск прерывается, стоимость записывается.
- После любой неповторяемой ошибки, исчерпанных повторов и HTTP 402 платный сбор **останавливается** до успешной ручной проверки: «Платный сбор остановлен после ошибки — запустите проверку вручную». Повторное задание никогда не начинает второй платный запуск, если ID запуска уже сохранён.
- **Расписание Apify (Schedule) не создавать.** Запускает только воркер, иначе сбор оплачивается дважды.

**Порядок.** Токен в `.env` → перезапуск → «Проверить подключение» (читает аккаунт и цены Actor, платного запуска нет) → «Настроить»: «Профили» (`@имя` или ссылка `tiktok.com/@имя`, до 20), «Публикаций за запуск с каждого профиля», «Загружать видео» (кадры для OCR; каждое видео увеличивает расход) → «Собрать сейчас». Расписание — по умолчанию раз в сутки (от 6 часов до недели). Стоимость каждого запуска — в его карточке.

**Поведение.** Запуск, опрос и чтение Dataset — фазами одного задания воркера, позиция в Dataset сохраняется. Файлы берутся только из хранилища Apify с Bearer-токеном, ссылки CDN TikTok не используются; файл считается загруженным, только когда байты сохранены. Видео режется на кадры для OCR; речь в роликах не распознаётся. Флаги `isAd` / `isSponsored` публикации не отсеивают. Вживую не проверено (токена нет): скачивание MP4 из хранилища Apify с токеном и учёт событийных списаний в `usageTotalUsd` — поэтому стоимость берётся по максимуму из отчёта Apify, событий по ценам Actor и оценки.

### 4.5. Krisha.kz — HTML-сборщик выдачи

API у Krisha нет, ключей не нужно — подключение сразу «настроено».

**Настройки.** «Настроить» → «URL поиска» (сервер принимает до 5 ссылок `https://krisha.kz/prodazha/…` или `/arenda/…`, например `https://krisha.kz/prodazha/kvartiry/ust-kamenogorsk/`) и при желании «Карточки объявлений» (до 10, для проверки). Без URL поиска сбор завершается ошибкой «Добавьте URL поиска Krisha»; проверка без настроек берёт выдачу по Усть-Каменогорску и контрольную карточку `https://krisha.kz/a/show/1009924986`. Расписание — по умолчанию раз в 6 часов (от 2 часов до недели).

**Лимиты.** `KRISHA_MIN_DELAY_S` (5 с, плюс случайные 0–2 с) — пауза между запросами; `Crawl-delay` из robots.txt учитывается, если он больше (не больше 60 с). `KRISHA_MAX_PAGES` (2) — страниц выдачи, `KRISHA_MAX_CARDS` (10) — карточек за запуск, не больше 30 запросов за запуск. robots.txt соблюдается: запрещённый адрес — ошибка «robots.txt Krisha запрещает …», а не пустая выдача.

**Проверка доступа (SafeLine, HTTP 468).** Сайт периодически отвечает на запрос карточки проверкой доступа. Обход не выполняется: ни подмены браузера, ни повторной отправки cookie, ни решения проверок, ни прокси.

- Закрыта карточка — запуск «частично» с заметкой «Карточки закрыты проверкой доступа (HTTP 468, SafeLine) — сохранены данные из выдачи».
- Закрыта страница поиска — статус «нужно ручное действие», автоматический сбор останавливается. Ручной шаг: открыть выдачу в обычном браузере и убедиться, что сайт доступен; при необходимости увеличить `KRISHA_MIN_DELAY_S` или период сбора; затем «Проверить подключение».
- `KRISHA_PLAYWRIGHT=1` — необязательная загрузка закрытой карточки браузером Playwright с выключенным JavaScript (скрипт проверки не выполняется). Playwright не входит в зависимости, ставится отдельно; этот путь **не проверялся**.

**Данные.** Из `window.data` берутся только поля по белому списку (сведения пользователя и служебные токены отбрасываются); описание, ЖК, застройщик и документы — из разметки карточки. Документы на странице — заявление продавца, не проверенное основание: в текст публикации они не попадают. Аккаунт публикации — «krisha.kz / <ЖК или тип продавца>». Сменилось фото или превью — новая версия публикации.

### 4.6. 2ГИС — геокодер

Это геоданные, а не сбор рекламы: кандидаты адреса для карточки ЖК или объекта открытых данных.

**Переменные.** `DGIS_API_KEY`. Квота: `DGIS_QUOTA_LIMIT` (900 запросов за период ключа) с даты `DGIS_QUOTA_PERIOD_START` (ГГГГ-ММ-ДД, начало периода в кабинете 2ГИС) и `DGIS_DAILY_LIMIT` (50 в сутки). `DGIS_CACHE_TTL_DAYS` (7) — сколько хранятся кандидаты. Счётчики — по отпечатку ключа: новый ключ считается заново. Локальный счётчик — оценка, точный расход — в кабинете 2ГИС. По плану подключения демо-ключ проекта действует до 16.11.2026 и даёт 1 000 запросов Geocoder за период — значение `DGIS_QUOTA_LIMIT` по умолчанию оставляет запас.

**Как пользоваться.**

1. Карточка ЖК (`/complexes/:id`) или объекта открытых данных (`/registry/:key`) → «Сверка адреса в 2ГИС» → «Сверить адрес». Запрос по умолчанию — «Казахстан, Усть-Каменогорск, {адрес}», его можно изменить. Сверку может запустить любой вошедший аналитик; «Обновить запрос» мимо кэша — только администратор.
2. Кандидаты — дом, город, корпус, точность, расстояние до точки в карточке. Метка «рекомендуется» — только у единственного точного дома в городе, и это подсказка: первый кандидат сам не выбирается.
3. «Принять» — выбор кандидата; отметка «Перенести координаты в карточку ЖК» (только у ЖК) меняет координаты и пишет в журнал «было → стало». Если точка в карточке изменилась после сверки — 409, координаты не меняются. «Отклонить всех» — ни один не подходит. Сведения открытых данных не меняются никогда.

Открытие карточки читает только сохранённые сверки — 2ГИС не запрашивается. Повтор того же адреса в пределах срока кэша — из кэша, без расхода квоты; новый запрос по тому же объекту — не чаще раза в 10 минут. Объект из рекламы (раздел 7.2) сверяется так же (`targetKind = discovered`, `POST /api/discovered/{id}/geo`). Запросов два: «Казахстан, Усть-Каменогорск, ЖК <название>» и адрес из рекламы, если он есть; интервал 10 минут считается по каждому из них. Координаты кандидата переходят в карточку ЖК только при её создании (`candidateId`). У карточки без координат (объект реестра без координат) «Перенести координаты» пишет в журнал «было нет координат → стало …». Квота и кэш — `GET /api/geo/status`. Порядок координат: у 2ГИС `{lat, lon}`, у ЖК `{lat, lng}`. Подложка карты остаётся прежней: геокодер карту 2ГИС не подключает.

### 4.7. OLX.kz — Partner API · OAuth (после одобрения заявки)

> **Ограничение.** Partner API даёт доступ только к ресурсам собственного авторизованного аккаунта — чтения чужих объявлений нет. Успешный OAuth не означает мониторинга объявлений, поэтому статус — «подключено · ограничено», сбора публикаций у OLX нет.

**Переменные.** `OLX_CLIENT_ID`, `OLX_CLIENT_SECRET` — выдаёт OLX после одобрения заявки. `OLX_REDIRECT_URI` — Callback URI из заявки: `https://your-domain.ngrok-free.dev/api/integrations/olx/callback`. `OLX_SCOPES` (по умолчанию `read v2`).

**Подключение.**

1. Ключи в `.env`, перезапуск API и воркера. Карточка OLX — «не подключён».
2. Запустить туннель ngrok на **порт API 8000** (не 5180) с тем же доменом, что в `OLX_REDIRECT_URI`, например `ngrok http --url=https://<домен> 8000` (в старых версиях ngrok — `--domain=<домен>`). Через этот хост API отвечает только на путь обратного вызова, остальное — 404 «Не найдено» (`PublicHostGuard`).
3. Режим администратора → «Подключить аккаунт OLX» (`POST /api/integrations/olx/start`) → открывается страница OLX, войти и разрешить доступ. Ссылка действует 10 минут и одноразовая; state привязан к отпечатку токена администратора.
4. OLX возвращает браузер на `GET /api/integrations/olx/callback`: сервер проверяет state, сам обменивает код на токены, проверяет аккаунт (`users/me`, заголовок `Version: 2.0`) и показывает простую страницу «OLX подключён: …». В журнале — «OLX: подключён аккаунт … (OAuth)».
5. Остановить туннель: для работы он больше не нужен.

Токены хранятся только в БД (без шифрования) и браузеру не отдаются. Воркер раз в сутки проверяет подключение и заранее обновляет токен доступа; если refresh token истёк (воркер долго не работал) — «Доступ OLX истёк — подключите аккаунт заново». «Отключить аккаунт» (`POST /api/integrations/olx/disconnect`) удаляет токены. Сменился адрес ngrok — обновить Redirect URI в кабинете OLX и `OLX_REDIRECT_URI` на сервере.

### 4.8. Приём публикаций API — `POST /api/intake/publications`

Для внешних сборщиков, которые присылают уже нормализованные публикации. Переменная — `INTEGRATION_INGEST_TOKEN`, заголовок — только `Authorization: Bearer`. Токен проверяется до разбора тела.

```bash
curl -s -X POST http://127.0.0.1:8000/api/intake/publications \
  -H "Authorization: Bearer <INTEGRATION_INGEST_TOKEN>" -H "Content-Type: application/json" \
  -d '{
    "platform": "tiktok",
    "externalId": "7000000000000000001",
    "account": "@example_developer",
    "url": "https://www.tiktok.com/@example_developer/video/7000000000000000001",
    "publishedAt": "2026-10-16T11:10:23Z",
    "collectedAt": "2026-10-16T12:00:00Z",
    "text": "Квартиры в новом ЖК, бронь 500 000 ₸",
    "media": [{"key": "cover", "url": "https://example.com/cover.jpg", "kind": "image"}],
    "sourceId": "my-collector",
    "externalRunId": "run-42"
  }'
# 201 {"status": "created", "adId": "…", "itemId": 1, "version": 1, "mediaQueued": 1, "analysisQueued": true}
```

- **Поля.** `platform`: `instagram`, `telegram`, `tiktok`, `krisha`, `olx`, `facebook`. `externalId` в каноническом виде: Telegram — «{ID канала}:{ID первого сообщения}», Instagram, TikTok и Krisha — число. Ещё `account`, `url` (http/https), `publishedAt` и `collectedAt` (с часовым поясом; `collectedAt` — не старше 30 дней и не в будущем), `text` (до 100 000 символов), `price`, `reach`, `media` (до 20 файлов, только `https://`, `kind` — `image` или `video`), `sourceId`, `externalRunId`, `raw`.
- **Нельзя.** Поля решений аналитика (`status`, `complexId`, `linkConfirmed…`, `termsReview…`, `origin`, `source`, `id` и др.) и неизвестные поля — 422.
- **Ответы.** Новая — 201 `created`; повтор без изменений — 200 `unchanged`; изменённая — 200 `updated` (новая версия, решения аналитика сохраняются, анализ заново). Публикация, собранная другим источником, — 409. Тело больше 2 МБ — 413. Нет токена — 401, неверный — 403, приём не настроен — 503.
- **Что хранится.** Все публикации приёма записываются от подключения «Приём публикаций API»; `sourceId`, `externalRunId` и заявленное `collectedAt` — в исходном снимке. Время получения публикации (`collectedAt` в ленте) — время сервера. Файлы по ссылкам скачивает задание анализа (только публичные адреса, с ограничением размера и типа), не сам запрос.

### 4.9. Claude (Anthropic) — анализ ИИ публикаций

Этап `llm` задания анализа (`backend/app/llm.py`; подключение `anthropic` — `backend/app/integrations/analyzer_anthropic.py`): после правил `saq-ai-1` Claude читает текст публикации и OCR и возвращает признаки продажи, суммы, кандидатов ЖК из переданного списка, неясности и краткую сводку. Всё — гипотезы: статус, привязку, подтверждение и вывод о нарушении модель не задаёт, баллы R1–R6 считает прежний движок. Без ключа этап не выполняется и ничего не пишет — работают одни правила; статус — «не настроен — нет `ANTHROPIC_API_KEY`». Публикации, собранные до появления ключа, дорабатываются постепенно в пределах дневного бюджета (ниже — «Дозапрос старых публикаций»).

- **Переменные.** `ANTHROPIC_API_KEY` — только на сервере. `ANTHROPIC_MODEL` — `claude-sonnet-5-5` (Claude Sonnet 5.5). `ANTHROPIC_EFFORT` — `medium` (low | medium | high | xhigh | max): глубина размышления, а с ней время и расход. `ANTHROPIC_MAX_TOKENS` — 16000 (ответ вместе с размышлением; 1024–64000). `ANTHROPIC_TIMEOUT_S` — 120 с (10–600). `ANTHROPIC_DAILY_BUDGET_USD` — 5.0 (0 — этап выключен; не больше 1000). `ANTHROPIC_BACKFILL_BATCH` — 5 (публикаций за проход дозапроса, 0–100; 0 — дозапрос выключен), `ANTHROPIC_BACKFILL_INTERVAL_MIN` — 10 (минут между проходами, 1–1440). `ANTHROPIC_WORKSPACE_ID` — ID рабочего пространства (`wrkspc_…`); нужен, только если ключ создан на уровне организации без привязки к пространству: иначе Anthropic отвечает HTTP 400 «This API key is not scoped to a workspace», и ID уходит заголовком `anthropic-workspace-id`. Неверное значение — значение по умолчанию и предупреждение с именем переменной, без значения.
- **Запрос.** Официальный SDK `anthropic` 1.15.0 (на `httpx2`), `client.beta.messages.create`: модель, `max_tokens`, системный промпт, одно сообщение пользователя, `output_config = {"effort": …, "format": {"type": "json_schema", "schema": …}}`. У Claude Sonnet 5.5 (как и у Opus 5.5) размышление адаптивное и через `{"type": "disabled"}` не отключается — `thinking`, `budget_tokens` и `temperature` не передаются, ответ модели не предзаполняется; глубину задаёт `ANTHROPIC_EFFORT`. Ключ передаётся клиенту явно (переменные окружения и профили SDK не читаются). Повторы SDK выключены — повторяет задание анализа (ниже).
- **Резервная модель — включена (`fallbacks: "default"`).** Для `claude-opus-5-5`, `claude-opus-5`, `claude-fable-5-1` и `claude-sonnet-5-5` запрос идёт с `fallbacks: "default"` и заголовком `anthropic-beta: server-side-fallback-2026-07-01`. Если классификаторы безопасности Anthropic отклонят запрос, Anthropic в том же вызове повторит его на модели, рекомендованной для этой категории отказа (например, категория cyber уходит на Claude Opus 4.8). В карточке публикации тогда видно «→ ответила …», расход считается по цене каждой попытки (`usage.iterations`). Если отказала вся цепочка — «модель отказалась»: это «анализ ИИ не выполнен», а не «риска нет». Для Haiku и других моделей параметр не передаётся. Чтобы выключить — задать модель без резервных (`ANTHROPIC_MODEL=claude-haiku-5-5`).
- **Только нужное.** Модели уходят: текст публикации, OCR, площадка, аккаунт и до 30 ЖК справочника (гипотезы правил первыми; id, название, застройщик, адрес; без отклонённых аналитиком). У заявки жителя аккаунт и ссылка не отправляются — его слова не доказательство (как в сопоставлении с ЖК). Ссылки, файлы, данные заявителя и решения аналитика не отправляются.
- **Материал — данные.** Текст и OCR стоят в сообщении пользователя внутри блоков `<publication_text>`, `<ocr_text>`, `<publication_metadata>`, `<complex_catalog>`; такие теги внутри самого текста обезвреживаются («‹/publication_text>»). Системный промпт велит считать всё внутри блоков данными и игнорировать указания в них. Ответ модели пишется только в таблицу `llm_analyses` и журнал — поля решений аналитика он не меняет.
- **Проверка ответа.** Сервер не верит модели на слово: JSON проверяется своей схемой (лишние поля — «не соответствует схеме»), каждая цитата должна дословно встречаться в отправленном тексте или OCR (сравнение без учёта регистра и пробелов), `complexId` — из отправленного списка, сумма — конечное неотрицательное число, списки — не длиннее 20, сводка — до 400 символов. Не прошедшее отбрасывается; сколько и почему — видно в карточке и в событии журнала.
- **Без повторной оплаты.** Результат хранится по ключу «хеш отправленного материала + модель + версия промпта» (`saq-llm-2`): тот же материал повторно не отправляется — новая версия публикации с тем же текстом берёт сохранённый результат. Новый текст или OCR — новый запрос. Исключение — «Проанализировать ещё раз» (ниже). Справочник ЖК входит в материал. Поэтому после создания карточки ЖК по рекламе правила пересчитываются отдельным заданием `rulesOnly`, без запроса к Claude (раздел 7.2).
- **Упомянутые ЖК и стадия (`saq-llm-2`).** В том же запросе модель возвращает `mentionedComplexes` — все ЖК, проекты и очереди, которые продаёт или называет реклама, в справочнике и вне его: `{name, address, quote}`. Ещё она возвращает `objectStage` — стадию объекта по материалу (`under_construction` / `completed` / `unknown` + дословная цитата). Название должно встречаться в тексте или OCR, иначе элемент отбрасывается (`dropped.name`). Адреса нет в материале — адрес очищается (`dropped.address`). Стадия без дословной цитаты — `unknown` (`dropped.stage`). После смены версии промпта дозапрос заново отправляет уже проанализированные публикации — в пределах дневного бюджета. Ответы `saq-llm-1` остаются строками истории и показываются, пока нет нового.
- **Сбои.** Сеть, 429 и 5xx — до 3 попыток: новое задание анализа через паузу задания (около 60 с, затем 120 с), но не раньше `retry-after` (не дольше 6 ч); правила и OCR при этом уже готовы. 401 — подключение «истёк доступ», 403 и 402 (оплата) — «нет доступа»: дальше этап пропускается без запросов, пока ключ не заменят (перезапуск API и воркера) или «Проверить подключение» не пройдёт. 400 и 404 — «не выполнен» без повтора, подключение — «ошибка». Отказ модели — «модель отказалась», ответ, обрезанный `ANTHROPIC_MAX_TOKENS`, — «не выполнен». Во всех случаях в журнале публикации — «Анализ ИИ (Claude) не выполнен: … — проверьте вручную», никогда «риск отсутствует».
- **Бюджет.** Перед запросом атомарно резервируется наихудшая стоимость (вход по оценке + весь `ANTHROPIC_MAX_TOKENS` на выходе — при 16000 у `claude-sonnet-5-5` около 0,17 $, у `claude-opus-5-5` около 0,33 $; фактическая стоимость обычно в разы меньше — она видна в карточке публикации), после ответа — поправка до оценки по `usage` (вход, выход, чтение и запись кэша). Цены за миллион токенов (вход / выход): `claude-opus-5-5` — 4 / 20 $, `claude-opus-5` и резервная `claude-opus-4-8` — 5 / 25 $, `claude-sonnet-5-5` — 2 / 10 $, `claude-haiku-5-5` — 0,10 / 0,50 $, `claude-fable-5-1` — 10 / 50 $, неизвестная модель — по самой дорогой цене. Счётчик — `quota_counters`, строка `anthropic-usd:<дата>` в микродолларах, день — по Усть-Каменогорску. Не хватает — этап пропускается с событием «Анализ ИИ (Claude) пропущен: дневной бюджет … исчерпан», подключение — «пауза: лимит»; это не цикл повторов: публикацию, пропущенную из-за бюджета, дозапрос возьмёт не раньше следующего дня. Запрос без ответа (сеть, 429, 5xx, 4xx) резерв возвращает. Оценка по прайсу — не счёт Anthropic: фактический расход — в консоли Anthropic.
- **Дозапрос старых публикаций.** Лидер воркера раз в `ANTHROPIC_BACKFILL_INTERVAL_MIN` минут ставит задания анализа собранным публикациям, у которых есть текст или OCR и нет ответа Claude по текущей версии промпта (`done`, `refused` или ответ, отброшенный проверкой). Ответ любой модели засчитывается — смена `ANTHROPIC_MODEL` не отправляет заново всё; новая версия промпта — отправляет. Порядок — новые первыми (время публикации в источнике, без него — время первого сбора). За проход — не больше `ANTHROPIC_BACKFILL_BATCH` вместе с ещё не выполненными заданиями дозапроса и не больше, чем покрывает остаток дневного бюджета по наихудшей стоимости каждого запроса; бюджет исчерпан, ключ не задан или отклонён, бюджет 0 — проход ничего не ставит. Пропускаются публикации с активным заданием анализа, ждущие повтора запроса (`retry_at`), с пропуском или сбоем этапа сегодня и уже получавшие задание дозапроса сегодня (день — по Усть-Каменогорску): повтор не раньше следующего дня, цикла нет. Задание дозапроса идёт после нового содержимого (приоритет −1); правила и OCR перезапускаются, но в журнал попадает только событие нового результата Claude (OCR — если изменился текст, файлы — по новым неудачам, гипотеза правил — если назначена привязка).
- **«Проанализировать ещё раз».** Кнопка в блоке «Анализ ИИ (Claude)» карточки собранной публикации; только в режиме администратора — запрос платный (`POST /api/ads/{id}/reanalyze`, `{author}`, `X-Admin-Token`). Сервер ставит задание анализа с флагом повторного анализа (приоритет 1): Claude получает тот же материал той же моделью снова, новый итог пишется новой строкой `llm_analyses`, прежний ответ остаётся строкой истории (`meta.materialHash` — исходный ключ материала, `meta.supersededAt` — когда заменён). В журнал — «Запрошен повторный анализ ИИ (Claude, модель …)» от автора (вид `ai`) и одно событие нового результата. Ответы: 202 — задание поставлено (задание анализа, уже стоящее в очереди, становится повторным анализом и выполняется сразу); 200 — анализ уже идёт или повторный анализ уже в очереди (без дубля и без события); 401/403/503 — токен администратора; 404 — нет публикации; 409 — публикация не собрана («Повторный анализ доступен для собранных публикаций»), нет текста и OCR, ключ отклонён, бюджет 0 или остатка дневного бюджета не хватает на запрос по наихудшей стоимости — задание не ставится; 503 — `ANTHROPIC_API_KEY` или пакет `anthropic` не заданы на сервере. Если к моменту выполнения бюджет кончился или ключ отклонили, прежний ответ остаётся в силе, в журнале — «Анализ ИИ (Claude) пропущен: …». После нажатия карточка опрашивает сервер, пока анализ не закончится, и показывает новый результат.
- **Проверка подключения.** «Проверить подключение» и `python -m app.integrations.smoke anthropic` вызывают `models.retrieve(ANTHROPIC_MODEL)` — сведения о модели, без генерации и без оплаты. Статусы: «не настроен» → «не проверен» → «готов» → «анализирует публикации» после первого анализа; «истёк доступ», «нет доступа», «ошибка», «пауза: лимит» (дневной бюджет), «не используется» (бюджет 0).
- **Где видно.** Карточка публикации — блок «Анализ ИИ (Claude)»: признаки продажи и суммы с цитатами (текст или OCR), кандидаты ЖК с пометкой «гипотеза — решение за аналитиком», неясности, модель, дата, токены и оценка стоимости, кнопка «Проанализировать ещё раз» (недоступна вне режима администратора, у несобранной публикации и пока идёт анализ — причина под кнопкой); при отказе, сбое или пропуске — «Анализ ИИ не выполнен … Это не значит, что риска нет». В API — поле `llm` публикации (`GET /api/ads`, `GET /api/ads/{id}`; request-id Anthropic и сырой ответ модели не выводятся). Журнал — событие «ИИ (Claude): признаки продажи — …; кандидаты ЖК — …; требует проверки аналитиком» от «Системы», без привязки к ЖК.
- **Приватность.** Текст публикации и распознанный OCR отправляются в Anthropic и обрабатываются по условиям Anthropic API. Это публичные рекламные тексты, но в них бывают телефоны и имена продавцов; данные заявителей из бота не отправляются. Если передача недопустима — не задавайте ключ.

## 5. Воркер

- **Запуск.** Docker — сервис `worker` (`python -m app.worker`, `restart: unless-stopped`, стартует после готовности API, `SAQ_WORKER_ID=worker-1`). `./dev.sh` запускает воркер сам после ответа API (`SAQ_WORKER=0` — без воркера). Вручную: `cd backend && .venv/bin/python -m app.worker`.
- **Схема БД.** Воркер схему не создаёт и не меняет: ждёт, пока API применит нужную версию («Воркер ждёт схему БД …»).
- **Один проход.** `python -m app.worker --once` — выполнить задания из очереди и выйти; `--schema-wait S` — сколько секунд ждать схему (с `--once` по умолчанию 0: схема не готова — выход с кодом 0); `--id` — имя воркера.
- **Пульс.** Поток-пульс раз в 30 с продлевает отметку воркера, аренду планировщика и блокировку текущего задания (`SAQ_JOB_LEASE_S`, 1800 с; не дольше `SAQ_JOB_MAX_S`, 3600 с — дальше зависшее задание вернётся в очередь). Нет пульса 120 с — страница «Подключения» пишет «Воркер сбора не запущен — проверки и сбор стоят в очереди».
- **Один планировщик.** Сборы по расписанию, плановые проверки и дозапрос Claude по старым публикациям (раз в `ANTHROPIC_BACKFILL_INTERVAL_MIN`) ставит только держатель аренды `scheduler`; выполнять задания может любой воркер (на PostgreSQL — `FOR UPDATE SKIP LOCKED`). Расписание Apify и другие внешние планировщики не используются.
- **Перезапуск.** Стабильный `SAQ_WORKER_ID` возвращает в очередь задания прошлого запуска этого воркера. SIGTERM — текущее задание дорабатывает (в Docker до 120 с), потом выход. Пауза опроса очереди — `SAQ_WORKER_POLL_S` (5 с).
- **Уборка раз в час.** Непривязанные ручные загрузки и файлы без записей старше суток, кандидаты 2ГИС старше срока кэша, истёкшие state OAuth, брошенные временные файлы.
- **Журнал.** `docker compose logs -f worker`. Секреты в журнал не попадают: маскируются все значения ключей, адреса с ключами не пишутся.

## 6. Файлы публикаций и резервные копии

- **Хранилище.** `MEDIA_ROOT`: локально `backend/data/media`, в Docker — том `media` (`/data/media`), общий для API и воркера. Файл хранится один раз по SHA-256 (`ab/cd/<sha256>.<ext>`), тип — по сигнатуре: JPEG, PNG, WEBP, GIF, MP4, MOV, WEBM. Пределы: `MEDIA_MAX_IMAGE_MB` (10), `MEDIA_MAX_VIDEO_MB` (200), свободное место `MEDIA_MIN_FREE_MB` (1024) — иначе 507 «Мало места для файлов на сервере — файл не сохранён». Отдаёт файлы `GET /api/media/{id}`.
- **Ручной скриншот.** Форма `/ads/new` загружает его на сервер (`POST /api/media`, до 10 МБ, не больше 50 файлов или 200 МБ непривязанных загрузок в час), и публикация ссылается на `/api/media/{id}` — скриншот открывается и после закрытия вкладки.
- **Резервная копия PostgreSQL** — перед каждым обновлением:

  ```bash
  docker compose exec db pg_dump -U saq saq > backup-$(date +%F).sql
  docker compose exec -T db psql -U saq saq < backup-YYYY-MM-DD.sql     # восстановление
  docker compose cp api:/data/media ./media-backup-$(date +%F)          # файлы публикаций
  ```

- **SQLite (`./dev.sh`).** База — `backend/saq.db`, файлы — `backend/data/media`. Перед обновлением схемы API сам делает копию `saq.db.bak-<старая версия>-<UTC>`.
- **Что секретно.** В БД и её копиях без шифрования лежат токены OLX и данные заявителей бота — хранить копии как секрет. Сессию Telegram в копию не включать. Стартовый набор (`shared/snapshot`, раздел 7.1) — не резервная копия: в нём нет токенов, заявок жителей, видео и служебных таблиц.
- **Осторожно.** `docker compose down -v` удаляет тома `pgdata`, `media` и `tgsession`: базу, файлы публикаций и сессию Telegram.

## 7. Обновление схемы БД

- Версия схемы — `2026.10-decisions-1` (`meta.schema_version`). Шаг `2026.10-decisions-1` только добавляет таблицу `screening_decisions` — решения аналитика по «Проверке по рекламе» (раздел 7.4); они невосстановимы и тоже защищают базу от пересоздания. Стартовый набор прежней версии загружается без неё (таблица пустая). Шаг `2026.10-verification-1` только добавляет nullable-столбцы: `complexes.published_list_check`, `complexes.appeals_check`, `appeals.comment`, `created_by`, `created_at`, `decided_by`, `decision_comment` (сверка сведений аналитиком, раздел 7.3). Сверка аналитика — невосстановимые данные: обращения `origin = analyst` и события журнала `data` не от «Системы» защищают базу от пересоздания при неизвестной версии схемы.
- Прежние шаги: версии `2026.10-verification-1`, `2026.10-discovery-1`. Базу прошлых версий API обновляет на месте при старте, ничего не удаляя: `2026.10-sources-1` — новые таблицы сбора и столбец `ads.collected_at`, затем таблица `llm_analyses` (результаты анализа ИИ); `2026.10-intake-1` — только `llm_analyses`. Шаг `2026.10-discovery-1` добавляет `discovered_objects` и `discovered_mentions` (объекты из рекламы) и снимает NOT NULL с `complexes.lat/lng`: ЖК бывает без координат. На PostgreSQL это `ALTER COLUMN … DROP NOT NULL`, на SQLite — пересборка таблицы `complexes` в транзакции шага, данные и индекс сохраняются. Строка прежнего анализатора в `collectors` остаётся (шаги только добавляют), её кода в реестре нет — её никто не читает. Шаги идемпотентны; на PostgreSQL два процесса не обновляют схему одновременно (advisory lock).
- Файловая SQLite перед обновлением копируется (`<db>.bak-<старая версия>-<UTC>`). PostgreSQL копирует оператор (`pg_dump`, раздел 6).
- Неизвестная или более старая версия: таблицы приложения пересоздаются (пустая БД снова получает стартовый набор, раздел 7.1), только если в базе нет невосстановимых данных — собранных публикаций, файлов, токенов OLX, заявок бота, сверок 2ГИС, оплаченных результатов анализа ИИ, настроек подключений, публикаций аналитиков. Иначе API не стартует и объясняет причину; принудительно — `SAQ_ALLOW_SCHEMA_RESET=1` (данные будут потеряны).
- Проверено в Docker: база `2026.10-sources-1` обновилась с сохранением данных. Шаг `2026.10-llm-1` проверен тестами на SQLite и PostgreSQL 16 (`test_intake_upgrade_adds_llm_table_and_keeps_data`), шаг `2026.10-discovery-1` — тоже (`test_discovery_upgrade_keeps_data_and_allows_missing_coords`).

### 7.1. Стартовый набор данных и демо-данные прежних версий

**Новое развёртывание** (пустой том `pgdata` или новая `backend/saq.db`) при первом старте API получает стартовый набор `shared/snapshot/` — реальные данные мониторинга на 18–19.10.2026: 23 ЖК (15 из открытого реестра, 8 по рекламе), 21 застройщик, 230 публикаций Instagram / Krisha / TikTok с OCR и 459 ответами Claude, 15 объектов из рекламы, журнал (1212 событий), 2 сигнала, настройки 5 подключений, 347 изображений (1024 px, JPEG q75). Подробно — README, «Развёртывание со стартовым набором данных»; модуль — `backend/app/snapshot.py`.

```bash
docker compose up --build                                                # пустая БД → «Пустая БД: загружен стартовый набор …» в журнале API
docker compose exec -T api python -m app.snapshot import                 # то же вручную (в непустую БД — отказ, ничего не меняется)
```

- **В непустую БД набор не загружается никогда** (есть строки хотя бы в одной таблице набора): обновление рабочей базы новой версией API её не трогает.
- **Подключения из набора** приходят с настройками и «включено», но в статусе «не проверено», без фактов, курсоров и расписания: ключи — только из `.env` нового сервера, подключения проверяются заново (раздел 2). Включённые сборщики начнут собирать, как только на сервере будут их ключи; уже собранные публикации распознаются по внешнему ID и не дублируются.
- **Анализ ИИ не повторяется:** ответы Claude по всем 230 публикациям — в наборе (`llm_analyses`); дозапрос (`ANTHROPIC_BACKFILL_*`) берёт только публикации без ответа текущей версии промпта.
- **Видео в набор не входят:** строка файла — «недоступно» с пояснением «не включено в стартовый набор — откройте оригинал» и ссылкой на оригинал; кадры видео не выгружены (их текст уже в `ads.ocr`). Повторный анализ публикации с видео («Проанализировать ещё раз») распознает только изображения.
- **Не входят** заявки жителей (`bot_submissions` — персональные данные), токены OLX, состояния OAuth, задания воркера, аренды, счётчики квот и бюджета, кэш кандидатов 2ГИС (решения аналитика — входят). Перед записью выгрузка проверяет файлы на значения секретов из настроек и токеноподобные строки.
- **Обновить набор** из рабочей БД — `python -m app.snapshot export` (только чтение; в Docker — в контейнере образа `api` с подключённым репозиторием, команда — в README). Набор прежней версии схемы загружается и новой версией кода (новые столбцы — NULL / значение по умолчанию), неизвестной — отказ: выгрузите заново.
- **Флаг** `meta.demo_data = purged` ставит и загрузка набора: демо-набора в приложении больше нет. Переменная `SAQ_DEMO_DATA` не читается — оставшаяся в `.env` строка даёт предупреждение при старте, её можно удалить.

**Базы прежних версий с вымышленным демо-набором** очищаются так (команды — из каталога с `docker-compose.yml`):

```bash
docker compose stop worker                                               # сбор и анализ не идут, пока меняются данные
docker compose exec -T db pg_dump -U saq saq > backup-$(date +%F).sql     # резервная копия (обязательно)
docker compose up -d --build api                                         # новая версия API, схема БД обновится при старте
docker compose exec -T api python -m app.demo purge --dry-run            # список: что удалится, что останется
docker compose exec -T api python -m app.demo purge --yes                # удаление (без --yes команда ничего не меняет)
docker compose up -d                                                     # воркер и фронтенд
```

- **Удаляется** только демо-набор: публикации, обращения, ЖК и застройщики с `origin = demo`, всё, что висит на демо-публикациях (журнал, анализы ИИ, записи приёма, файлы, задания, заявки бота), сигналы, проверки 2ГИС и события журнала по демо-ЖК, явные события журнала демо-набора (`demo.SEED_AUDIT`). Собранные и внесённые публикации остаются — привязка к демо-ЖК снимается с записью «Привязка снята: демо-ЖК «…» удалён».
- **Остаются** аналитики (вход), открытый реестр (`source_records`), карточки ЖК из реестра, подключения, запуски сбора, файлы, задания, анализы ИИ собранных публикаций, счётчики квот и бюджета.
- **Флаг** `meta.demo_data = purged` ставится в той же транзакции; повторный `purge` ничего не удаляет.
- **SQLite** (`./dev.sh`): `cd backend && .venv/bin/python -m app.demo purge --yes` сначала копирует базу в `saq.db.bak-demo-purge-<UTC>`.
- **Вернуть демо-набор нельзя** — он остался только у тестов (`shared/testdata`). Офлайн-режим фронтенда (без бэкенда) показывает копию стартового набора только для чтения (`shared/snapshot/api`).
- **Карточки ЖК из реестра** создаёт и дополняет (только пустые поля) `python -m app.demo import-registry`; API вызывает его при каждом старте сам (на свежем стартовом наборе — без изменений). Риск по такой карточке не оценивается, пока нет проверенных сведений (подтверждённая привязка публикации, сверенный документ, проверенное обращение, снимок площадки) — сигнал по ней до этого не создаётся. Карточки создаются по всем 15 объектам. У 3 объектов без координат (`r-ab-residence-2`, `r-diamond`, `r-prestizh-sparkle-diamond`) `lat`/`lng` — `null` до сверки 2ГИС. Повторный импорт дополняет координаты, если у карточки их нет, а у источника они появились.

### 7.2. ЖК по рекламе: объекты из рекламы, импорт, «Проверка по рекламе»

Многих рекламируемых ЖК в открытом реестре нет. Claude (`saq-llm-2`) выписывает из каждой публикации все упомянутые ЖК. Те, которых нет ни в справочнике ЖК, ни в открытом реестре, становятся **объектами из рекламы** (`GET /api/discovered`). Название сравнивается без «ЖК», кавычек и регистра, латиница ≈ кириллица, номер очереди не важен. Код — `backend/app/discovery.py`.

1. **Разбор.** `GET /api/discovered?status=new` — новые объекты: сколько публикаций, какие аккаунты, когда впервые и в последний раз упомянут, до трёх дословных цитат со ссылкой на публикацию, стадия по рекламе, признаки продажи, последние сверки 2ГИС, оценка. Заявки жителей учитываются (`sources.bot`), но их аккаунт в «аккаунты рекламы» не попадает.
2. **2ГИС.** `POST /api/discovered/{id}/geo` `{author}` — кандидаты по названию и адресу из рекламы (раздел 4.6).
3. **Решение** — автор в журнал, `kind = data`:
   - `create-complex` `{author, name, address?, lat?, lng?, developerName?, developerBin?, candidateId?}` — карточка ЖК `origin = advertised`;
   - `link` `{author, complexId}` — объект — другое написание существующего ЖК;
   - `dismiss` `{author, reason}` — не ЖК, подборка, ошибка.

   После `create-complex` правила пересчитываются по публикациям с упоминаниями (задание `rulesOnly`, без Claude). Формальный риск карточки `advertised` не оценивается до проверенных сведений.
4. **Импорт списком** (администратор). Через API или из консоли:

   ```bash
   curl -X POST http://localhost:8000/api/discovered/import -H "X-Admin-Token: $SAQ_ADMIN_TOKEN" \
        -H 'Content-Type: application/json' -d @advertised.json      # {"author": "…", "note": "…", "items": [...]}
   docker compose cp advertised.json api:/tmp/advertised.json            # файл — в контейнер API (список или {"note", "items"})
   docker compose exec -T api python -m app.demo add-advertised --file /tmp/advertised.json --author "Омарова Ж." --note "разбор 18.10"
   ```

   Строка: `{"name": "ЖК «Nova Park»", "aliases": ["Нова Парк"], "address": "ул. Абая, 10", "lat": 49.95, "lng": 82.6, "developerName": "ТОО «Nova Build»", "developerBin": "123456789012", "accounts": ["@novapark.uka"], "sourceUrls": ["https://www.instagram.com/p/…"], "note": "…"}`. Обязательно только `name`; координаты — парой; ссылки — только `http(s)`. Повтор идемпотентен: у той же карточки дополняются пустые адрес и координаты, другие названия, аккаунты и ссылки. ЖК, который есть в реестре или справочнике, пропускается с причиной.

**«Проверка по рекламе»** — поле `screening` у ЖК (`GET /api/complexes`) и застройщиков (`GET /api/developers`), сводка — в `GET /api/stats`. Это предварительная автоматическая оценка, а не вывод о нарушении. Формальный риск, статусы публикаций и привязки она не меняет. Основание (`permit`): `permitted` — у Homeportal есть документ основания, в Казреестре (Ashyq Data — набор разрешений) есть запись объекта или аналитик сверил «есть»; `not_permitted` — раздел Homeportal «Без разрешения на дольщиков» (сведения источника, не юридический вывод) или аналитик сверил «нет» по гарантии ЕО и разрешению МИО; `unknown` — сведений нет. Сверка аналитика важнее открытых данных (раздел 7.3).

| Статус | Правило |
|---|---|
| `ok` | `permitted`, конфликта стадии нет |
| `check` | `permitted`, но объект «Завершён» у источника, а свежая реклама — старт продаж или строящийся объект; основания нет, но свежая реклама с признаками говорит «дом сдан» (цитата) или карточка «введён»; «Без разрешения на дольщиков» без свежей рекламы с признаками; реклама без признаков; карточка по рекламе без публикаций |
| `suspect` | основания нет и есть свежая (`SAQ_SCREENING_DAYS`, 120 дней) реклама с признаком приёма денег (старт продаж, бронь, ДДУ, рассрочка, взнос), по которой объект не сдан |
| `unknown` | нет ни основания, ни рекламы |
| `ok` «Дом сдан — замечаний нет», `variant: commissioned` | решение аналитика «Объект сдан» (акт, дата акта, источник) — важнее статусов выше, пока не снято новой рекламой (раздел 7.4) |
| `ok` «Проверено — замечаний нет», `variant: analyst` | решение аналитика «Проверено — замечаний нет» (что проверено, источник) — так же |
| снято новой рекламой (`decision.status = reopened`) | после решения к ЖК отнесена публикация с признаком приёма денег (у «сдан» — только старт продаж, «строится» или новая очередь): статус снова автоматический, первая причина — «Новая реклама после решения аналитика (<дата>): …» |

Застройщик получает `suspect`, если подозрителен хотя бы один его ЖК, `ok` — если все его ЖК `ok` (в реестре, сданы или проверены аналитиком), `unknown` — если ЖК нет, иначе `check`.

### 7.3. Сверка сведений аналитиком

Карточки ЖК из реестра и по рекламе — сведения источника: основание, перечень ГАСК, готовность, обращения и снимки сверяет аналитик в карточке ЖК (README, «Сверка сведений аналитиком»). Маршруты — для вошедшего аналитика, токен администратора не нужен; автор — в журнал (`kind = data`):

```bash
curl -X POST http://localhost:8000/api/complexes/r-orda/basis -H 'Content-Type: application/json' \
     -d '{"author": "Омарова Ж.", "doc": "mio", "value": "yes", "ref": "№ 1383/МҚЗТ-С-331 от 13.10.2025",
          "source": "Homeportal", "sourceUrl": "https://homeportal.kz/ru/projects/1329"}'
# 200 — ЖК: basis.mio = "yes", basis.sources.mio = {ref, source, url, checkedAt, checkedBy}, permit = {status: "permitted",
#        source: "analyst", verified: true, text: "Основание сверено: разрешение МИО — есть (Homeportal, 19.10.2026)"}
# журнал: «Основание сверено: разрешение МИО — есть (№ 1383/МҚЗТ-С-331 от 13.10.2025), источник: Homeportal
#          (https://homeportal.kz/ru/projects/1329), сверено 19.10.2026»
curl http://localhost:8000/api/complexes/r-orda/basis    # что сверено и что называет реестр (suggestion)
```

- **Старшинство в «Проверке по рекламе».** Сверка аналитика («есть»/«нет» с источником и датой) важнее записей открытых данных: «есть» по любому документу → `permitted` (`source = analyst`); «нет» по гарантии ЕО и разрешению МИО → `not_permitted` (как R1; участие БВУ без разрешения МИО основанием не бывает); затем раздел Homeportal «Без разрешения на дольщиков», затем документ Homeportal — кроме документа того вида, который аналитик сверил «нет», затем запись Казреестра. «Есть»/«нет» без источника или даты сверкой не считается.
- **R4.** У карточки реестра и рекламы пустой список обращений — «нужна проверка» (обращения в систему никто не заносил), пока аналитик не отметит «Обращений нет — сверено» (`POST /api/complexes/{id}/appeals-check`). У демо-ЖК — как прежде. Заявки жителей через бота по-прежнему становятся публикациями (`source = bot`), а не обращениями.
- **Снимки площадки** лежат в том же хранилище, что файлы публикаций (том `media`, раздел 6): запись `media_assets` с `origin_ref = site`, без публикации; уборка непривязанных скриншотов их не удаляет. Часовой лимит ручных загрузок (50 файлов / 200 МБ) — общий со скриншотами формы.
- **Демо-ЖК** (тестовый набор, `shared/testdata`). Без действий аналитика риск демо-набора тот же (эталон `shared/testdata/risk_golden.json`, часть `seed`, не менялся). Основание демо-ЖК «Шығыс Тауэр» (c4: гарантии ЕО и разрешения МИО нет, с источником) в «Проверке по рекламе» теперь `not_permitted`, как и его R1; статус оценки тот же.

### 7.4. Решение аналитика по «Проверке по рекламе»: «Объект сдан», «Проверено — замечаний нет»

Сданный, но всё ещё рекламируемый ЖК и другие случаи «Требует проверки», которые аналитик проверил, закрываются решением в карточке ЖК (блок «Решение аналитика»). Автор — вошедший аналитик (`HumanName`, «Система» — 422), событие журнала `data`. Код — `backend/app/decisions.py`, правила — `backend/app/screening.py`.

```bash
curl -X POST http://localhost:8000/api/complexes/a-nomad/commissioned -H 'Content-Type: application/json' \
     -d '{"author": "Омарова Ж.", "actNumber": "12", "actDate": "2026-09-01", "source": "ЕГКН", "sourceUrl": "https://…"}'
# 200 — ЖК: screening = {status: "ok", label: "Дом сдан — замечаний нет", variant: "commissioned", basis: "confirmed",
#        reasons[0] = {kind: "decision", text: "Сдан: акт № 12 от 01.09.2026, источник ЕГКН; подтвердил: Омарова Ж., 19.10.2026"}},
#        decision = {kind: "commissioned", status: "active", …}, stage = "введён"
# журнал: «Объект сдан — ввод в эксплуатацию подтверждён: акт № 12 от 01.09.2026, источник: ЕГКН (https://…);
#          стадия карточки: не указана → «введён»»
curl -X POST http://localhost:8000/api/complexes/r-asylym/screening-decision -H 'Content-Type: application/json' \
     -d '{"author": "Омарова Ж.", "decision": "no_issues", "reason": "Сверено с ГАСК: дом сдан, продажи по гарантии ЕО",
          "source": "Ответ акимата / ГАСК"}'
curl -X DELETE http://localhost:8000/api/complexes/a-nomad/screening-decision -H 'Content-Type: application/json' \
     -d '{"author": "Омарова Ж.", "reason": "Акт относится к другой очереди"}'   # оценка снова автоматическая, стадия — прежняя
curl http://localhost:8000/api/complexes/a-nomad/screening-decisions          # история: active / cancelled / superseded
```

- **Проверка входа** (422, по-русски): дата акта — обязательна, `ГГГГ-ММ-ДД`, не позже сегодня и не раньше 2000 года; источник — обязателен; ссылка — `http(s)://`; номер акта — до 128 символов; «что проверено» — не короче 10 символов; причина отмены — не короче 5 символов. Нет ЖК — 404; отменять нечего — 404; `DELETE …/commissioned`, когда действует «проверено», — 409.
- **Хранение.** Строка `screening_decisions`: действующее решение (`active`) — одно на ЖК (частичный уникальный индекс, запись — под блокировкой строки ЖК); новое решение заменяет прежнее (`superseded`), отмена — `cancelled` (кто, когда, причина). «Сдан» запоминает прежнюю стадию (`prev_stage`) и ставит «введён»; отмена или замена другим видом решения её возвращает. Строки не удаляются, они входят в стартовый набор.
- **Снятие новой рекламой** вычисляется при каждом чтении и в БД не пишется: публикация, отнесённая к ЖК (те же правила отнесения, что у оценки), вышла не раньше минуты решения (местное время; дата без времени — со следующего дня) и несёт признак приёма денег; у «сдан» — ещё и строящийся объект или новая очередь (стадия по рекламе «строится», признак «старт продаж», слова «строится», «новая очередь», «котлован», «на этапе строительства» в тексте). Обычная продажа квартир (и рассрочка) в сданном доме решение не снимает. Решение снова действует, если эту публикацию отклонили, отметили «это не предложение внести деньги» или отклонили привязку; либо аналитик записывает новое решение (отсчёт — от него).
- **Риск.** Отметка «сдан» меняет только стадию карточки: формальный риск считает объект введённым по прежним правилам (R1, R2, R3, R5, R6 — «объект введён в эксплуатацию»; Python и TS не менялись). Карточка реестра или рекламы без других проверенных сведений по-прежнему «риск не оценивается».

## 8. Безопасность

- **Секреты** — только в `.env` на сервере: не в Git, не в образе (`.dockerignore`), не во фронтенде (в переменные `VITE_*` и код страниц ключи не попадают; токен администратора вводит человек). API не возвращает значения секретов — только имена недостающих переменных и ссылки вида `env:ИМЯ`. Журналы маскируют все значения ключей, адреса запросов с ключами не пишутся.
- **Доступ.** Три отдельных токена (администратор, приём, бот), без заданного токена маршрут закрыт (503), сравнение — за постоянное время. Отказы приёма и бота видны в статусе подключения.
- **Порты.** `db` и `api` опубликованы только на `127.0.0.1`. Фронтенд `web` (5180) слушает все интерфейсы и проксирует `/api` — запускать на доверенной сети.
- **Публичный адрес.** Для хоста из `OLX_REDIRECT_URI` (туннель ngrok) открыт только путь обратного вызова OLX (`PublicHostGuard`, проверяются `Host` и `X-Forwarded-Host`), остальные пути — 404. Туннель держать включённым только на время шага OAuth.
- **Файлы публикаций** доступны любому, кто достучится до API: `GET /api/media/{id}` и `GET /api/ads` без авторизации.
- **Загрузчик файлов** ходит только на публичные адреса (DNS закрепляется при соединении, внутренние сети запрещены на каждом перенаправлении), с пределами размера, типа и времени, без cookie.
- **Сессия Telegram** — файл 0600 в каталоге 0700 с проверкой владельца, в Docker — отдельный том только у воркера; одновременно ею пользуется один процесс.
- **Контейнеры** работают от непривилегированного пользователя (uid 10001); ffmpeg разбирает недоверенные видео с ограничениями ресурсов (`prlimit`).
- **Заявки жителей не доказательство**: аккаунт и ссылка из заявки в гипотезе ЖК не учитываются и в Anthropic не отправляются, данные заявителя отделены от публикации.
- **Анализ ИИ (Claude)**: ключ `ANTHROPIC_API_KEY` — только на сервере, передаётся клиенту SDK явно и маскируется в журналах; текст публикаций и OCR уходят в Anthropic (раздел 4.9, «Приватность»); ответ модели — гипотезы, решений аналитика он не меняет.
- **Без обхода защит**: ни для Krisha, ни для других источников.
- **Организационно.** Сервису нужны токены, ключи и сессии, а не пароли от Facebook, Google и почты. Разработчикам лучше выдать роли в кабинетах Meta, Apify, OLX и 2ГИС, чем передавать пароли.

## 10. Что нужно от владельца аккаунтов

1. **Meta** — пользовательский токен с разрешениями из раздела 4.1 (долгосрочный или токен системного пользователя).
2. **Telegram** — код входа (SMS или сообщение Telegram на телефон аккаунта для чтения каналов) в течение 15 минут после `--send-code`; пароль 2FA, если он включён.
3. **Apify** — API-токен и согласованный дневной лимит расходов.
4. **OLX** — одобрение заявки, `OLX_CLIENT_ID` и `OLX_CLIENT_SECRET`.
5. **Anthropic** — ключ API `ANTHROPIC_API_KEY` (необязательно): включает анализ ИИ Claude; согласовать дневной бюджет `ANTHROPIC_DAILY_BUDGET_USD` и передачу текста публикаций в Anthropic.
6. **Бот заявок** — проект `saq-telegram-bot`, чтобы сверить контракт приёмника.
7. **Krisha** — ничего: карточки могут закрываться проверкой доступа SafeLine, это ограничение сайта, обход не выполняется.
