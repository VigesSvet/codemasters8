# Подключение источников рекламы — инструкция оператора

Состояние на 17.10.2026. Как включить каждый источник публикаций, проверить его и что делать при ошибке. Требования — план подключения от 16.10.2026, краткий обзор и таблица статусов — раздел «Подключение источников рекламы» в [README](../README.md). Реальных ключей, паролей, сессий и телефонов в этом документе нет: только имена переменных.

## 1. Как устроено

```text
Instagram — Meta Graph API ───────┐
Telegram-каналы — MTProto ────────┤  воркер: задания «проверка» и «сбор»
TikTok — Apify (платно) ──────────┤  (по кнопке администратора или по расписанию)
Krisha.kz — HTML выдачи ──────────┘
Telegram-бот заявок ── POST /api/intake/telegram ─────┐
Внешний сборщик ────── POST /api/intake/publications ─┤
                                                       ▼
        единый приём: дедупликация по внешнему ID, версии, файлы → БД + хранилище MEDIA_ROOT
                                                       ▼
        задание анализа: файлы → кадры видео (ffmpeg) → OCR (Tesseract) → правила saq-ai-1
                                                       ▼
        публикация «Новая» в ленте, гипотезы ИИ и журнал от «Системы» → решение аналитика → балл → сигнал → PDF

2ГИС → кандидаты адреса в карточке ЖК → выбор аналитика (координаты меняются только явным решением)
OLX → OAuth собственного аккаунта, без чтения чужих объявлений
OpenAI → не подключён (только статус)
```

- **Два процесса.** API (`uvicorn app.main:app`) отдаёт состояние, принимает публикации и заявки и ставит задания в таблицу `jobs`. Воркер (`python -m app.worker`) — единственный, кто выполняет проверки, сбор и анализ, и единственный планировщик. В HTTP-запросе пользователя сбор не выполняется: «Проверить подключение» и «Собрать сейчас» отвечают 202 и номером запуска.
- **Таблицы.** `collectors` (подключение: настройки, состояние, отметка «остановлен»), `collection_runs` (запуски: время, статус, счётчики, ID запуска Apify, стоимость), `ingest_items` и `ingest_versions` (исходная запись и история изменений), `media_assets` (файлы), `jobs`, `worker_leases`, `oauth_states`, `integration_tokens`, `geo_checks`, `bot_submissions`, `quota_counters`. С таблицами демо-набора они связаны только по `ads.id` (без внешних ключей).
- **Собранная публикация.** `origin = collected`, `source = parser` (сборщики и приём через API) или `bot` (заявка жителя), статус `new`. Привязку к ЖК анализ не назначает: гипотезы ИИ видны аналитику, решение — за ним (`SAQ_COLLECTED_AUTOLINK=1` включает правило ручного ввода только для демонстрации). Автор автоматических событий журнала — «Система»; имя «Система» людям на новых маршрутах использовать нельзя.
- **Сбой ≠ «нет новых».** Ошибка ключа, закрытый канал, изменившаяся разметка, запрет robots.txt, проверка доступа на сайте — это статус ошибки источника, а не пустая выдача. «Нет новых» — только запуск без ошибок и без записей.

## 2. Статусы подключения

| Статус | Что значит | Что делать |
|---|---|---|
| не настроен | На сервере нет переменных (их имена показаны в карточке) или условия (сессии Telegram) | Заполнить `.env`, перезапустить API и воркер |
| не проверен | Ключи есть, проверки ещё не было или ключи изменились после неё | «Проверить подключение» |
| в очереди / проверяется / идёт сбор | Задание ждёт воркер или выполняется | Ждать; если долго «в очереди» — проверить, запущен ли воркер (раздел 5) |
| готов к сбору (у 2ГИС — «готов») | Проверка прошла | Настроить списки, «Собрать сейчас» или включить «Сбор по расписанию» |
| работает | Последний сбор успешен; у бота — «принимает заявки», у приёма API — «принимает публикации» | — |
| работает частично | Часть данных недоступна: закрытый канал, карточки Krisha за проверкой доступа, окно выдачи TikTok | Прочитать заметки запуска |
| ожидает заявок / ожидает публикаций | Приёмник настроен, данных ещё не было | — |
| ошибка | Сбой источника или ошибка настроек | Текст ошибки в карточке и в журнале; исправить, «Проверить подключение» |
| истёк доступ | Токен истёк (Meta, OLX) | Обновить токен (разделы 4.1, 4.7) |
| нет доступа | У токена нет разрешений или клиент приёма/бот присылает неверный токен | Проверить разрешения и токены |
| нужно ручное действие | Сайт закрыл страницы проверкой доступа (Krisha) | Раздел 4.5; обход не выполняется |
| пауза: лимит запросов | Источник ограничил частоту (Graph API, FloodWait Telegram, 2ГИС) | Сбор продолжится после указанного времени |
| не используется | OpenAI: ключ задан, но анализатор в этой версии не подключён | — |
| остановлен (метка) | Платный сбор после ошибки или ошибка настроек: расписание не запускает сбор | Исправить причину, «Проверить подключение» (снимает остановку при успехе) |

У OLX свои подписи: «заявка отправлена» (ключей нет), «не подключён» (ключи есть, OAuth не пройден), «подключено · ограничено» (аккаунт подключён; это не сбор чужих объявлений). Статусы запуска: в очереди, выполняется, успешно, частично, ошибка, проверка доступа на сайте, пауза: лимит запросов, не настроен, отменён.

Если ключ на сервере сменился после последней успешной проверки, карточка пишет «Ключи на сервере изменились после последней проверки — перезапустите воркер и нажмите «Проверить подключение»», и сбор по расписанию не запускается до новой проверки.

## 3. Общая подготовка

### 3.1. Файл `.env`

```bash
cp .env.example .env            # в корне репозитория; .env — вне Git и вне Docker-образа
python3 -c "import secrets; print(secrets.token_urlsafe(32))"   # по отдельному значению на каждый токен
```

- Значения пишутся без кавычек и читаются буквально. Пустое значение — то же, что не задано: подключение «не настроено» и ничего не запрашивает.
- Три токена доступа: `SAQ_ADMIN_TOKEN` (администратор подключений), `INTEGRATION_INGEST_TOKEN` (внешние сборщики), `SERVICE_API_TOKEN` (бот заявок). Каждый — не короче 24 символов и не меньше 12 разных; токен администратора не может совпадать с двумя другими. Слабый или совпадающий токен считается не заданным (предупреждение в журнале API называет переменную, но не значение).
- Настройки читаются один раз при старте процесса. После правки `.env`: в Docker — `docker compose up -d api worker`, локально — перезапуск `./dev.sh`.
- Docker передаёт `.env` в `api` и `worker` через `env_file` (формат `raw`, без подстановок). `MEDIA_ROOT` и `TG_SESSION_PATH` в Docker задаёт `docker-compose.yml` (`/data/media`, `/data/private/telegram.session`) — значения из `.env` для них не действуют. Локально приложение само читает `.env` из корня репозитория (в окружение оболочки он не загружается); другой файл — `SAQ_ENV_FILE`.

### 3.2. Режим администратора в интерфейсе

Настройка подключений и ручной запуск — только администратору; демо-вход аналитика этого права не даёт.

1. `/sources` → раздел «Подключения» → «Режим администратора» → ввести значение `SAQ_ADMIN_TOKEN`. Сервер проверяет его (`GET /api/admin/check`); токен хранится только в `sessionStorage` этой вкладки до её закрытия и уходит заголовком `X-Admin-Token` лишь в маршруты администратора.
2. Действия в карточке подключения: «Проверить подключение», «Настроить» (аккаунты, каналы, профили, URL поиска; «Период сбора, минут»), «Сбор по расписанию», «Собрать сейчас»; в шапке раздела — «Обновить всё» (сбор для включённых, настроенных и проверенных сборщиков, остальные — с причиной пропуска). У OLX — «Подключить аккаунт OLX». Автор действий — вошедший аналитик.
3. Без `SAQ_ADMIN_TOKEN` на сервере маршруты администратора отвечают 503 «Администрирование подключений не настроено: задайте SAQ_ADMIN_TOKEN на сервере».

Из консоли — тот же заголовок (или `Authorization: Bearer`):

```bash
curl -s -X POST http://127.0.0.1:8000/api/sources/krisha/test \
  -H "X-Admin-Token: <SAQ_ADMIN_TOKEN>" -H "Content-Type: application/json" -d '{"author": "Имя аналитика"}'
```

Порядок для любого сборщика: ключи в `.env` → перезапуск → «Проверить подключение» → «готов к сбору» → «Настроить» → «Собрать сейчас» или «Сбор по расписанию».

### 3.3. Проверка из консоли

```bash
cd backend && .venv/bin/python -m app.integrations.smoke              # все подключения
cd backend && .venv/bin/python -m app.integrations.smoke dgis krisha  # выбранные
docker compose exec worker python -m app.integrations.smoke           # в Docker: у воркера есть том сессии Telegram
```

Коды: `instagram`, `telegram`, `tiktok`, `krisha`, `telegram_bot`, `intake`, `dgis`, `openai`, `olx`. Для каждого — «код: статус — пояснение» и несекретные сведения. Без ключей сеть не используется. Публикации не сохраняются, но запросы к источникам настоящие: 2ГИС расходует квоту в кабинете (локальный счётчик не учитывает), Krisha получает обычные запросы, Apify — только чтение аккаунта и цен Actor, без платного запуска. Код выхода 0 (это отчёт), 2 — неизвестный код. Значения ключей не печатаются.

## 4. Подключения

### 4.1. Instagram — Meta Graph API · Business Discovery

**Переменные.** `META_USER_ACCESS_TOKEN` (обязательно). `META_APP_ID` и `META_APP_SECRET` — по желанию: с ними срок токена проверяется токеном приложения, а к каждому запросу добавляется `appsecret_proof`. `META_GRAPH_VERSION` (по умолчанию `v26.0`). Где искать наш Instagram: `META_IG_USER_ID` (17840000000000001), иначе Страницы токена с учётом `META_PAGE_ID` (1000000000000002), иначе Страницы бизнес-портфолио `META_BUSINESS_ID` (1000000000000001). Лимиты: `IG_PAGE_SIZE` (25 публикаций на запрос), `IG_FIRST_LOAD_MAX` (50 при первой загрузке аккаунта).

**Получить токен.**

1. [Graph API Explorer](https://developers.facebook.com/tools/explorer/) под аккаунтом Facebook с ролью в приложении и на Странице. «Meta App» — приложение проекта (его App ID — `META_APP_ID`), «User or Page» — «User Token».
2. Разрешения: обязательные `instagram_basic`, `instagram_manage_insights`, `pages_read_engagement`; рекомендуемые `pages_show_list`, `business_management` (без них Страница находится только по `META_IG_USER_ID` или `META_BUSINESS_ID`). Если роль на Странице выдана через Business Manager, Meta требует ещё `ads_read` или `ads_management`. «Generate Access Token» и подтвердить доступ к Странице и Instagram.
3. Полученный токен краткосрочный (около часа). В [Access Token Debugger](https://developers.facebook.com/tools/debug/accesstoken/) вставить его, «Debug» — проверить App ID, Scopes и Expires, затем «Extend Access Token»: получится долгосрочный токен (около 60 дней). То же сервером: `GET https://graph.facebook.com/v26.0/oauth/access_token?grant_type=fb_exchange_token&client_id=<META_APP_ID>&client_secret=<META_APP_SECRET>&fb_exchange_token=<краткосрочный токен>` — выполнять только на сервере, App Secret не вводить в браузере. Вместо пользовательского токена можно выпустить токен системного пользователя в Business Manager с теми же разрешениями.
4. Записать токен в `META_USER_ACCESS_TOKEN`, перезапустить API и воркер, «Проверить подключение». Успех: «Подключено: @… Токен действует до ДД.ММ.ГГГГ».
5. «Настроить» → аккаунты наблюдения (`@имя` или ссылка `instagram.com/имя`, только профессиональные аккаунты) → «Собрать сейчас» или «Сбор по расписанию» (по умолчанию раз в час, от 30 минут до суток).

**Продление.** Пока сбор включён, воркер раз в сутки проверяет токен (`debug_token`). За 7 дней до истечения в карточке появляется «Токен истекает ДД.ММ.ГГГГ — продлите его», при скором окончании доступа к данным — «Доступ к данным истекает … — пройдите вход Meta заново». Продление — те же шаги 1–4: новый токен в Explorer, «Extend Access Token», замена в `.env`, перезапуск, «Проверить подключение». Токен, истекающий в ближайшие сутки, включить не даст: «Токен Meta краткосрочный — получите долгосрочный (60 дней) или токен системного пользователя». Истёкший или отозванный токен — статус «истёк доступ».

**Поведение.** Запросы — на `graph.facebook.com/{META_GRAPH_VERSION}/`, токен только в заголовке `Authorization: Bearer`. Ссылки на файлы временные, поэтому файлы скачиваются при сборе (только с CDN Instagram/Facebook). Карусели — со слайдами; если Business Discovery слайдов не отдаёт, сохраняется первое изображение с заметкой (вживую это не проверялось — токена ещё нет). При использовании лимита Graph API от 80 % запуск прекращает запросы, следующий откладывается на час. Таргетированные показы конкретным людям так не видны — только публикации аккаунтов из списка.

### 4.2. Telegram-каналы — MTProto (Telethon)

**Переменные.** `TG_API_ID`, `TG_API_HASH` — с [my.telegram.org](https://my.telegram.org) («API development tools») выделенного аккаунта для чтения каналов. `TG_PHONE` — номер этого аккаунта, нужен только для входа. `TG_SESSION_PATH` — файл сессии (локально по умолчанию `backend/data/private/telegram.session`, в Docker — `/data/private/telegram.session` на томе `tgsession`, смонтированном только в воркер). Лимиты: `TG_HISTORY_LIMIT` (50 сообщений канала в первый запуск), `TG_EDIT_WINDOW` (правки среди последних 30 сообщений), `TG_MAX_VIDEO_MB` (50), `TG_DOWNLOAD_TIMEOUT_S` (300). `BOT_TOKEN` для сбора каналов не подходит.

**Вход — один раз, по коду.** Сессией одновременно пользуется только один процесс (блокировка `<путь>.lock`), поэтому воркер на время входа останавливают. Код приходит в приложение Telegram или SMS на телефон аккаунта; владелец сообщает его в течение 15 минут (дальше ожидание кода устаревает). Не пересылайте код сообщением в самом Telegram — Telegram может отклонить такой вход.

Локально (воркер остановлен: `./dev.sh` выключен или запущен с `SAQ_WORKER=0`):

```bash
cd backend
.venv/bin/python -m app.integrations.telegram_login --send-code    # «Код отправлен (…). Введите: … --code <код>»
.venv/bin/python -m app.integrations.telegram_login --code 12345   # код из Telegram или SMS
.venv/bin/python -m app.integrations.telegram_login --password     # только если ответ «Нужен пароль двухфакторной защиты»
.venv/bin/python -m app.integrations.telegram_login --status       # «Сессия есть: @имя»
```

В Docker:

```bash
docker compose stop worker
docker compose run --rm worker python -m app.integrations.telegram_login --send-code
docker compose run --rm worker python -m app.integrations.telegram_login --code 12345
docker compose run --rm worker python -m app.integrations.telegram_login --password   # пароль вводится скрыто
docker compose run --rm worker python -m app.integrations.telegram_login --status
docker compose up -d worker
```

Без аргументов команда проходит вход за один запуск: запрашивает код и пароль в терминале. `--force` — войти заново при существующей сессии, `--logout` — выйти и удалить файл сессии. Коды выхода: 0 — готово, 1 — ошибка, 2 — не заданы `TG_API_ID` / `TG_API_HASH` / `TG_PHONE`, 3 — нужен пароль 2FA, 4 — неверный код или пароль, 5 — код устарел (снова `--send-code`), 6 — Telegram просит подождать, 7 — сессия занята воркером. Номер, код и сессия не печатаются.

**После входа.** Запустить воркер → «Настроить» → каналы (`t.me/имя`, `@имя` или ссылка; только публичные, ссылки-приглашения отклоняются) → «Проверить подключение» → «Собрать сейчас» или расписание (по умолчанию раз в 30 минут, от 15 минут до суток). Файл сессии создаётся с правами 0600 в каталоге 0700; это секрет — в Git и в резервные копии его не кладут, при потере проще войти заново.

**Поведение.** Первый запуск — последние `TG_HISTORY_LIMIT` сообщений, дальше — только новые после сохранённой позиции и правки в окне `TG_EDIT_WINDOW`. Альбом — одна публикация (ID «канал:первое сообщение») со всеми файлами. FloodWait — «пауза: лимит запросов» без повторов внутри запуска. Закрытый или несуществующий канал — «работает частично» с причиной; если недоступны все — ошибка настроек.

### 4.3. Telegram-бот заявок — приёмник `POST /api/intake/telegram`

> **Контракт не сверен с адаптером `saq-telegram-bot`** (`integration/telegram_intake.py`): проекта бота на этой машине нет. Ниже — то, что реализует приёмник этой версии API. Перед подключением бота сверить маршруты, заголовок и формат тела с кодом адаптера.

- **Переменная.** `SERVICE_API_TOKEN` — тот же секрет, что `SERVICE_API_TOKEN` в настройках бота. Свои переменные бот читает сам (`BOT_TOKEN`, `ADMIN_USER_IDS`, `ADMIN_CHAT_ID`, `SERVICE_URL`, `SERVICE_API_TOKEN`); `INTEGRATION_INGEST_TOKEN` с ним не совместим.
- **Доступ.** `Authorization: Bearer <SERVICE_API_TOKEN>` или `X-API-Key: <SERVICE_API_TOKEN>`. Нет секрета на сервере — 503, нет заголовка — 401, неверный — 403. Отказы видны в карточке: бот с неверным токеном — «нет доступа», отклонённая заявка — «ошибка», а не «ожидает заявок».
- **Маршруты.** `POST /api/intake/telegram` — заявка: `application/json` (до 1 МБ, без файлов) или `multipart/form-data` с полем `payload` (JSON заявки) и повторяющимся полем `files` (до 10 файлов по 20 МБ; JPEG, PNG, WEBP, GIF, MP4, MOV; тип — по содержимому). `GET /api/intake/telegram/submissions/{externalId}` — статус заявки. `GET /api/intake/telegram/updates?since=<ISO с поясом>&limit=1..500` — заявки, статус которых изменился позже `since`.
- **Тело заявки.** `externalId` (повторяемый ID от бота, например «chat_id:message_id»), `submittedAt`, `platform` (`instagram`, `telegram`, `tiktok`, `krisha`, `olx`, `facebook`, `other`), `account`, `url`, `text`, `comment`, `applicant` (`telegramUserId`, `chatId`, `username`, `name`, `phone`), `media` (описание файлов по порядку: `key`, `fileName`, `mime`). Поля решений аналитика и неизвестные поля — 422.
- **Ответы.** Новая заявка — 201 `created`, повторная доставка — 200 `unchanged` (копия не создаётся), изменённая — 200 `updated` (новая версия). Статусы для жителя: `received`, `in_review`, `confirmed`, `dismissed` с русскими подписями.
- **Хранение.** Публикация попадает в общую ленту (`source = bot`, статус «Новая», без привязки к ЖК) и в очередь анализа. Данные заявителя и его комментарий — только в `bot_submissions`: в публикации, журнале и ответах API их нет. Аккаунт и ссылка со слов жителя в гипотезе ЖК не учитываются.
- **`SERVICE_URL` бота.** Не `localhost` внутри контейнера бота. Если бот в Docker и подключён к сети этого compose-проекта (внешняя сеть `codemasters8_default`), адрес API — `http://api:8000`; если бот запущен на этой же машине без Docker — `http://127.0.0.1:8000` (API опубликован только на 127.0.0.1). Нужен ли в `SERVICE_URL` префикс `/api`, решает адаптер — сверить.
- **Один экземпляр.** На один токен бота — один процесс long polling; webhook и polling одновременно не использовать.

### 4.4. TikTok — Apify, Actor `clockworks/tiktok-scraper` (платно)

**Переменные.** `APIFY_TOKEN` — личный API-токен из Apify Console (Settings → API & Integrations). `APIFY_ACTOR_ID` (по умолчанию `clockworks~tiktok-scraper`). Ключи TikTok Developer не нужны. Input без секретов — `backend/app/integrations/tiktok_input.json` (новые публикации профиля, видео, обложки и изображения слайд-шоу).

**Защита от расходов.**

- `APIFY_MAX_TOTAL_CHARGE_USD` (0,5) — лимит на один запуск; передаётся Apify как есть и никогда не повышается. Меньше минимума Actor или больше дневного лимита — ошибка настроек с пояснением.
- `APIFY_DAILY_BUDGET_USD` (1,0) — лимит на сутки по времени Усть-Каменогорска. Учитываются и неудачные оплаченные запуски, и запуски с неизвестной стоимостью (по лимиту на запуск). Исчерпан — «Дневной лимит расходов Apify (…) исчерпан».
- `APIFY_MAX_ITEMS_PER_PROFILE` (5) — публикаций с профиля за запуск; если все они новые, более ранние могли выпасть — запуск «частично». `APIFY_RUN_TIMEOUT_S` (300) — после срока запуск прерывается, стоимость записывается.
- После любой неповторяемой ошибки, исчерпанных повторов и HTTP 402 платный сбор **останавливается** до успешной ручной проверки: «Платный сбор остановлен после ошибки — запустите проверку вручную». Повторное задание никогда не начинает второй платный запуск, если ID запуска уже сохранён.
- **Расписание Apify (Schedule) не создавать.** Запускает только воркер, иначе сбор оплачивается дважды.

**Порядок.** Токен в `.env` → перезапуск → «Проверить подключение» (читает аккаунт и цены Actor, платного запуска нет) → «Настроить»: «Профили» (`@имя` или ссылка `tiktok.com/@имя`, до 20), «Публикаций за запуск с каждого профиля», «Загружать видео» (кадры для OCR; каждое видео увеличивает расход) → «Собрать сейчас». Расписание — по умолчанию раз в сутки (от 6 часов до недели). Стоимость каждого запуска — в его карточке.

**Поведение.** Запуск, опрос и чтение Dataset — фазами одного задания воркера, позиция в Dataset сохраняется. Файлы берутся только из хранилища Apify с Bearer-токеном, ссылки CDN TikTok не используются; файл считается загруженным, только когда байты сохранены. Видео режется на кадры для OCR; речь в роликах не распознаётся. Флаги `isAd` / `isSponsored` публикации не отсеивают. Вживую не проверено (токена нет): скачивание MP4 из хранилища Apify с токеном и учёт событийных списаний в `usageTotalUsd` — поэтому стоимость берётся по максимуму из отчёта Apify, событий по ценам Actor и оценки.

### 4.5. Krisha.kz — HTML-сборщик выдачи

API у Krisha нет, ключей не нужно — подключение сразу «настроено».

**Настройки.** «Настроить» → «URL поиска» (сервер принимает до 5 ссылок `https://krisha.kz/prodazha/…` или `/arenda/…`, например `https://krisha.kz/prodazha/kvartiry/ust-kamenogorsk/`) и при желании «Карточки объявлений» (до 10, для проверки). Без URL поиска сбор завершается ошибкой «Добавьте URL поиска Krisha»; проверка без настроек берёт выдачу по Усть-Каменогорску и контрольную карточку `https://krisha.kz/a/show/1009924986`. Расписание — по умолчанию раз в 6 часов (от 2 часов до недели).

**Лимиты.** `KRISHA_MIN_DELAY_S` (5 с, плюс случайные 0–2 с) — пауза между запросами; `Crawl-delay` из robots.txt учитывается, если он больше (не больше 60 с). `KRISHA_MAX_PAGES` (2) — страниц выдачи, `KRISHA_MAX_CARDS` (10) — карточек за запуск, не больше 30 запросов за запуск. robots.txt соблюдается: запрещённый адрес — ошибка «robots.txt Krisha запрещает …», а не пустая выдача.

**Проверка доступа (SafeLine, HTTP 468).** Сайт периодически отвечает на запрос карточки проверкой доступа. Обход не выполняется: ни подмены браузера, ни повторной отправки cookie, ни решения проверок, ни прокси.

- Закрыта карточка — запуск «частично» с заметкой «Карточки закрыты проверкой доступа (HTTP 468, SafeLine) — сохранены данные из выдачи».
- Закрыта страница поиска — статус «нужно ручное действие», автоматический сбор останавливается. Ручной шаг: открыть выдачу в обычном браузере и убедиться, что сайт доступен; при необходимости увеличить `KRISHA_MIN_DELAY_S` или период сбора; затем «Проверить подключение».
- `KRISHA_PLAYWRIGHT=1` — необязательная загрузка закрытой карточки браузером Playwright с выключенным JavaScript (скрипт проверки не выполняется). Playwright не входит в зависимости, ставится отдельно; этот путь **не проверялся**.

**Данные.** Из `window.data` берутся только поля по белому списку (сведения пользователя и служебные токены отбрасываются); описание, ЖК, застройщик и документы — из разметки карточки. Документы на странице — заявление продавца, не проверенное основание: в текст публикации они не попадают. Аккаунт публикации — «krisha.kz / <ЖК или тип продавца>». Сменилось фото или превью — новая версия публикации.

### 4.6. 2ГИС — геокодер

Это геоданные, а не сбор рекламы: кандидаты адреса для карточки ЖК или объекта открытых данных.

**Переменные.** `DGIS_API_KEY`. Квота: `DGIS_QUOTA_LIMIT` (900 запросов за период ключа) с даты `DGIS_QUOTA_PERIOD_START` (ГГГГ-ММ-ДД, начало периода в кабинете 2ГИС) и `DGIS_DAILY_LIMIT` (50 в сутки). `DGIS_CACHE_TTL_DAYS` (7) — сколько хранятся кандидаты. Счётчики — по отпечатку ключа: новый ключ считается заново. Локальный счётчик — оценка, точный расход — в кабинете 2ГИС. По плану подключения демо-ключ проекта действует до 16.11.2026 и даёт 1 000 запросов Geocoder за период — значение `DGIS_QUOTA_LIMIT` по умолчанию оставляет запас.

**Как пользоваться.**

1. Карточка ЖК (`/complexes/:id`) или объекта открытых данных (`/registry/:key`) → «Сверка адреса в 2ГИС» → «Сверить адрес». Запрос по умолчанию — «Казахстан, Усть-Каменогорск, {адрес}», его можно изменить. Сверку может запустить любой вошедший аналитик; «Обновить запрос» мимо кэша — только администратор.
2. Кандидаты — дом, город, корпус, точность, расстояние до точки в карточке. Метка «рекомендуется» — только у единственного точного дома в городе, и это подсказка: первый кандидат сам не выбирается.
3. «Принять» — выбор кандидата; отметка «Перенести координаты в карточку ЖК» (только у ЖК) меняет координаты и пишет в журнал «было → стало». Если точка в карточке изменилась после сверки — 409, координаты не меняются. «Отклонить всех» — ни один не подходит. Сведения открытых данных не меняются никогда.

Открытие карточки читает только сохранённые сверки — 2ГИС не запрашивается. Повтор того же адреса в пределах срока кэша — из кэша, без расхода квоты; новый запрос по тому же объекту — не чаще раза в 10 минут. Квота и кэш — `GET /api/geo/status`. Порядок координат: у 2ГИС `{lat, lon}`, у ЖК `{lat, lng}`. Подложка карты остаётся прежней: геокодер карту 2ГИС не подключает.

### 4.7. OLX.kz — Partner API · OAuth (после одобрения заявки)

> **Ограничение.** Partner API даёт доступ только к ресурсам собственного авторизованного аккаунта — чтения чужих объявлений нет. Успешный OAuth не означает мониторинга объявлений, поэтому статус — «подключено · ограничено», сбора публикаций у OLX нет.

**Переменные.** `OLX_CLIENT_ID`, `OLX_CLIENT_SECRET` — выдаёт OLX после одобрения заявки. `OLX_REDIRECT_URI` — Callback URI из заявки: `https://your-domain.ngrok-free.dev/api/integrations/olx/callback`. `OLX_SCOPES` (по умолчанию `read v2`).

**Подключение.**

1. Ключи в `.env`, перезапуск API и воркера. Карточка OLX — «не подключён».
2. Запустить туннель ngrok на **порт API 8000** (не 5180) с тем же доменом, что в `OLX_REDIRECT_URI`, например `ngrok http --url=https://<домен> 8000` (в старых версиях ngrok — `--domain=<домен>`). Через этот хост API отвечает только на путь обратного вызова, остальное — 404 «Не найдено» (`PublicHostGuard`).
3. Режим администратора → «Подключить аккаунт OLX» (`POST /api/integrations/olx/start`) → открывается страница OLX, войти и разрешить доступ. Ссылка действует 10 минут и одноразовая; state привязан к отпечатку токена администратора.
4. OLX возвращает браузер на `GET /api/integrations/olx/callback`: сервер проверяет state, сам обменивает код на токены, проверяет аккаунт (`users/me`, заголовок `Version: 2.0`) и показывает простую страницу «OLX подключён: …». В журнале — «OLX: подключён аккаунт … (OAuth)».
5. Остановить туннель: для работы он больше не нужен.

Токены хранятся только в БД (без шифрования) и браузеру не отдаются. Воркер раз в сутки проверяет подключение и заранее обновляет токен доступа; если refresh token истёк (воркер долго не работал) — «Доступ OLX истёк — подключите аккаунт заново». «Отключить аккаунт» (`POST /api/integrations/olx/disconnect`) удаляет токены. Сменился адрес ngrok — обновить Redirect URI в кабинете OLX и `OLX_REDIRECT_URI` на сервере.

### 4.8. Приём публикаций API — `POST /api/intake/publications`

Для внешних сборщиков, которые присылают уже нормализованные публикации. Переменная — `INTEGRATION_INGEST_TOKEN`, заголовок — только `Authorization: Bearer`. Токен проверяется до разбора тела.

```bash
curl -s -X POST http://127.0.0.1:8000/api/intake/publications \
  -H "Authorization: Bearer <INTEGRATION_INGEST_TOKEN>" -H "Content-Type: application/json" \
  -d '{
    "platform": "tiktok",
    "externalId": "7000000000000000001",
    "account": "@example_developer",
    "url": "https://www.tiktok.com/@example_developer/video/7000000000000000001",
    "publishedAt": "2026-10-16T11:10:23Z",
    "collectedAt": "2026-10-16T12:00:00Z",
    "text": "Квартиры в новом ЖК, бронь 500 000 ₸",
    "media": [{"key": "cover", "url": "https://example.com/cover.jpg", "kind": "image"}],
    "sourceId": "my-collector",
    "externalRunId": "run-42"
  }'
# 201 {"status": "created", "adId": "…", "itemId": 1, "version": 1, "mediaQueued": 1, "analysisQueued": true}
```

- **Поля.** `platform`: `instagram`, `telegram`, `tiktok`, `krisha`, `olx`, `facebook`. `externalId` в каноническом виде: Telegram — «{ID канала}:{ID первого сообщения}», Instagram, TikTok и Krisha — число. Ещё `account`, `url` (http/https), `publishedAt` и `collectedAt` (с часовым поясом; `collectedAt` — не старше 30 дней и не в будущем), `text` (до 100 000 символов), `price`, `reach`, `media` (до 20 файлов, только `https://`, `kind` — `image` или `video`), `sourceId`, `externalRunId`, `raw`.
- **Нельзя.** Поля решений аналитика (`status`, `complexId`, `linkConfirmed…`, `termsReview…`, `origin`, `source`, `id` и др.) и неизвестные поля — 422.
- **Ответы.** Новая — 201 `created`; повтор без изменений — 200 `unchanged`; изменённая — 200 `updated` (новая версия, решения аналитика сохраняются, анализ заново). Публикация, собранная другим источником, — 409. Тело больше 2 МБ — 413. Нет токена — 401, неверный — 403, приём не настроен — 503.
- **Что хранится.** Все публикации приёма записываются от подключения «Приём публикаций API»; `sourceId`, `externalRunId` и заявленное `collectedAt` — в исходном снимке. Время получения публикации (`collectedAt` в ленте) — время сервера. Файлы по ссылкам скачивает задание анализа (только публичные адреса, с ограничением размера и типа), не сам запрос.

### 4.9. OpenAI — не подключён

`OPENAI_API_KEY` и `OPENAI_MODEL` только показывают статус: без ключа — «не настроен», с ключом — «не используется». Анализ выполняют правила `saq-ai-1` на сервере; внешний анализатор и локальный классификатор в очередь не подключены.

## 5. Воркер

- **Запуск.** Docker — сервис `worker` (`python -m app.worker`, `restart: unless-stopped`, стартует после готовности API, `SAQ_WORKER_ID=worker-1`). `./dev.sh` запускает воркер сам после ответа API (`SAQ_WORKER=0` — без воркера). Вручную: `cd backend && .venv/bin/python -m app.worker`.
- **Схема БД.** Воркер схему не создаёт и не меняет: ждёт, пока API применит нужную версию («Воркер ждёт схему БД …»).
- **Один проход.** `python -m app.worker --once` — выполнить задания из очереди и выйти; `--schema-wait S` — сколько секунд ждать схему (с `--once` по умолчанию 0: схема не готова — выход с кодом 0); `--id` — имя воркера.
- **Пульс.** Поток-пульс раз в 30 с продлевает отметку воркера, аренду планировщика и блокировку текущего задания (`SAQ_JOB_LEASE_S`, 1800 с; не дольше `SAQ_JOB_MAX_S`, 3600 с — дальше зависшее задание вернётся в очередь). Нет пульса 120 с — страница «Подключения» пишет «Воркер сбора не запущен — проверки и сбор стоят в очереди».
- **Один планировщик.** Сборы по расписанию и плановые проверки ставит только держатель аренды `scheduler`; выполнять задания может любой воркер (на PostgreSQL — `FOR UPDATE SKIP LOCKED`). Расписание Apify и другие внешние планировщики не используются.
- **Перезапуск.** Стабильный `SAQ_WORKER_ID` возвращает в очередь задания прошлого запуска этого воркера. SIGTERM — текущее задание дорабатывает (в Docker до 120 с), потом выход. Пауза опроса очереди — `SAQ_WORKER_POLL_S` (5 с).
- **Уборка раз в час.** Непривязанные ручные загрузки и файлы без записей старше суток, кандидаты 2ГИС старше срока кэша, истёкшие state OAuth, брошенные временные файлы.
- **Журнал.** `docker compose logs -f worker`. Секреты в журнал не попадают: маскируются все значения ключей, адреса с ключами не пишутся.

## 6. Файлы публикаций и резервные копии

- **Хранилище.** `MEDIA_ROOT`: локально `backend/data/media`, в Docker — том `media` (`/data/media`), общий для API и воркера. Файл хранится один раз по SHA-256 (`ab/cd/<sha256>.<ext>`), тип — по сигнатуре: JPEG, PNG, WEBP, GIF, MP4, MOV, WEBM. Пределы: `MEDIA_MAX_IMAGE_MB` (10), `MEDIA_MAX_VIDEO_MB` (200), свободное место `MEDIA_MIN_FREE_MB` (1024) — иначе 507 «Мало места для файлов на сервере — файл не сохранён». Отдаёт файлы `GET /api/media/{id}`.
- **Ручной скриншот.** Форма `/ads/new` загружает его на сервер (`POST /api/media`, до 10 МБ, не больше 50 файлов или 200 МБ непривязанных загрузок в час), и публикация ссылается на `/api/media/{id}` — скриншот открывается и после закрытия вкладки.
- **Резервная копия PostgreSQL** — перед каждым обновлением:

  ```bash
  docker compose exec db pg_dump -U saq saq > backup-$(date +%F).sql
  docker compose exec -T db psql -U saq saq < backup-YYYY-MM-DD.sql     # восстановление
  docker compose cp api:/data/media ./media-backup-$(date +%F)          # файлы публикаций
  ```

- **SQLite (`./dev.sh`).** База — `backend/saq.db`, файлы — `backend/data/media`. Перед обновлением схемы API сам делает копию `saq.db.bak-<старая версия>-<UTC>`.
- **Что секретно.** В БД и её копиях без шифрования лежат токены OLX и данные заявителей бота — хранить копии как секрет. Сессию Telegram в копию не включать.
- **Осторожно.** `docker compose down -v` удаляет тома `pgdata`, `media` и `tgsession`: базу, файлы публикаций и сессию Telegram.

## 7. Обновление схемы БД

- Версия схемы — `2026.10-intake-1` (`meta.schema_version`). Базу прошлой версии `2026.10-sources-1` API обновляет на месте при старте: добавляет новые таблицы и столбец `ads.collected_at`, ничего не удаляя. Шаги идемпотентны; на PostgreSQL два процесса не обновляют схему одновременно (advisory lock).
- Файловая SQLite перед обновлением копируется (`<db>.bak-<старая версия>-<UTC>`). PostgreSQL копирует оператор (`pg_dump`, раздел 6).
- Неизвестная или более старая версия: таблицы приложения пересоздаются из сида, только если в базе нет невосстановимых данных — собранных публикаций, файлов, токенов OLX, заявок бота, сверок 2ГИС, настроек подключений, публикаций аналитиков. Иначе API не стартует и объясняет причину; принудительно — `SAQ_ALLOW_SCHEMA_RESET=1` (данные будут потеряны).
- Проверено в Docker: база прошлой схемы обновилась с сохранением данных.

## 8. Безопасность

- **Секреты** — только в `.env` на сервере: не в Git, не в образе (`.dockerignore`), не во фронтенде (в переменные `VITE_*` и код страниц ключи не попадают; токен администратора вводит человек). API не возвращает значения секретов — только имена недостающих переменных и ссылки вида `env:ИМЯ`. Журналы маскируют все значения ключей, адреса запросов с ключами не пишутся.
- **Доступ.** Три отдельных токена (администратор, приём, бот), без заданного токена маршрут закрыт (503), сравнение — за постоянное время. Отказы приёма и бота видны в статусе подключения.
- **Порты.** `db` и `api` опубликованы только на `127.0.0.1`. Фронтенд `web` (5180) слушает все интерфейсы и проксирует `/api` — запускать на доверенной сети.
- **Публичный адрес.** Для хоста из `OLX_REDIRECT_URI` (туннель ngrok) открыт только путь обратного вызова OLX (`PublicHostGuard`, проверяются `Host` и `X-Forwarded-Host`), остальные пути — 404. Туннель держать включённым только на время шага OAuth.
- **Файлы публикаций** доступны любому, кто достучится до API: `GET /api/media/{id}` и `GET /api/ads` без авторизации.
- **Загрузчик файлов** ходит только на публичные адреса (DNS закрепляется при соединении, внутренние сети запрещены на каждом перенаправлении), с пределами размера, типа и времени, без cookie.
- **Сессия Telegram** — файл 0600 в каталоге 0700 с проверкой владельца, в Docker — отдельный том только у воркера; одновременно ею пользуется один процесс.
- **Контейнеры** работают от непривилегированного пользователя (uid 10001); ffmpeg разбирает недоверенные видео с ограничениями ресурсов (`prlimit`).
- **Заявки жителей не доказательство**: аккаунт и ссылка из заявки в гипотезе ЖК не учитываются, данные заявителя отделены от публикации.
- **Без обхода защит**: ни для Krisha, ни для других источников.
- **Организационно.** Сервису нужны токены, ключи и сессии, а не пароли от Facebook, Google и почты. Разработчикам лучше выдать роли в кабинетах Meta, Apify, OLX и 2ГИС, чем передавать пароли.
